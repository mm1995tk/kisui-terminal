# kisui-terminal

[日本語](README.ja.md)

kisui-terminal is a terminal-centered workspace that works closely with [shijimi-editor](https://github.com/mm1995tk/shijimi-editor): it splits a window into panes and runs terminals (with `shj` inside), videos, images, PDFs and a file tree in them. The name is 汽水 (kisui, brackish water), where the shijimi clam lives.

It is a separate app from shijimi-editor, with its own version and releases. It ships with the `shj` it was tested with, and the terminals in its panes use that `shj` first (the `shj` you install yourself is still used outside kisui-terminal). How kisui-terminal and `shj` talk to each other is written in [docs/protocol.md](docs/protocol.md); the two share no code.

## Install

Linux (x86_64 and aarch64) and macOS on Apple silicon (arm64); macOS on Intel is not supported, neither as the app nor as a remote machine. Every release is at [Releases](https://github.com/mm1995tk/kisui-terminal/releases); the AppImage and the `.dmg` update themselves.

- **AppImage**: `chmod +x kisui-terminal-linux-*.AppImage` and run it. The AppImages are added to the latest release once every two weeks, so a new release may have only the `.dmg` for a while.
- **`.dmg`**: the app is not signed by Apple, so macOS refuses to open it the first time. Drag `kisui-terminal.app` to Applications, open it once (macOS says it cannot be verified; close that dialog), then go to **System Settings → Privacy & Security** and press **Open Anyway** next to the line about `kisui-terminal`. From then on it opens normally. Or run `xattr -dr com.apple.quarantine /Applications/kisui-terminal.app` once. The app is only ad-hoc signed, so after each update you need to grant again the permissions you gave it under Privacy & Security (such as **App Management**).

The nightly build of main is `kisui-terminal-nightly` in the [`nightly` pre-release](https://github.com/mm1995tk/kisui-terminal/releases/tag/nightly) (a `.dmg` only; on Linux, use Nix for the nightly). It has its own name and identifier, so it can be installed next to the stable one.

With Nix, kisui-terminal is the `kisui-terminal` package (`kisui-terminal-nightly` for the nightly, installed under that name), or `programs.kisui-terminal.enable = true;` in home-manager with the flake's `homeManagerModules.default`. Built with Nix it has no auto update: update it with `nix flake update`. If you install the app another way (the .dmg on macOS, say) and only want home-manager to place the settings, write `programs.kisui-terminal.package = null;` (no package is installed). `programs.kisui-terminal.channel` chooses the folder of the settings: `"stable"` for `~/.config/kisui-terminal/`, `"nightly"` for `~/.config/kisui-terminal-nightly/`. Unset, it follows the package name when there is a package, and is `"stable"` when `package = null`; a `channel` that differs from the package is an evaluation error. Example: `programs.kisui-terminal = { enable = true; package = null; channel = "nightly"; settings = { /* ... */ }; };`

```sh
nix run github:mm1995tk/kisui-terminal
nix profile install github:mm1995tk/kisui-terminal
nix profile install github:mm1995tk/kisui-terminal#kisui-terminal-nightly
```

## Using it

The manual of shijimi-editor explains how `shj` behaves inside kisui-terminal: the panes it opens, videos, opening a URL and the file tree. See its pages [Terminal](https://mm1995tk.github.io/shijimi-editor/manual/terminal/), [Browser](https://mm1995tk.github.io/shijimi-editor/manual/browser/) and [Configuration files](https://mm1995tk.github.io/shijimi-editor/manual/config/).

In a pane, `kisui open <file|url>` shows an image right there in the pane you typed it in, at the cursor, the way `icat` of kitty does (it writes the image to the terminal with kitty's graphics protocol, so it works in the panes of a remote machine too; PNG, JPEG, GIF (the first frame), WebP and BMP, as wide as the pane at most). Other files open in a pane of the same workspace, by their kind: a video, a PDF (by the extension, or by the first bytes when the extension does not tell). A pane of each kind replaces the one already open. `kisui open --pane <image>` opens an image in a pane of its own instead. SVG and AVIF images, images over 16 MB or 10000 pixels, and an image when stdout is not a terminal (a pipe, the shell of a coding agent) open in a pane without `--pane`. An `http`/`https` URL opens in the browser of the computer kisui-terminal runs on (no pane): in a new tab of the workspace when the built-in browser is on (`[gui.browser]` below), otherwise in your OS default browser. A URL that `shj` asks to open goes the same way. A `localhost` URL from a remote (ssh) machine opens through a relay that kisui-terminal runs over a plain ssh session (`kisui relay` on that machine; no ssh port forwarding, so it works where port forwarding is refused too), so it shows the page of the remote machine. It works in the panes of a remote machine too, and only in the panes of kisui-terminal: from any other shell it refuses. `kisui --help` lists the commands.

```sh
kisui open ./diagram.png         # in this pane
kisui open --pane ./diagram.png  # in a pane of its own
kisui open ./talk.mp4
kisui open ./paper.pdf
kisui open https://example.com/
```

`kisui notify <text>` shows a desktop notification on the computer the window runs on, to tell you that a long command has ended. `kisui clipboard copy` puts the text of stdin on that computer's clipboard, and `kisui clipboard paste` prints the text on it. Since reading your clipboard is risky, kisui-terminal asks you every time `paste` reads it, and prints it only when you allow it. All three work the same in the panes of a remote machine.

```sh
make build; kisui notify "build: $?"
echo hello | kisui clipboard copy
kisui clipboard paste > note.txt
```

In the shell of a pane, `pbcopy` and `pbpaste` call `kisui clipboard copy` and `kisui clipboard paste` (`echo hello | pbcopy`), and `pbpaste` asks you every time too. This works the same in the panes of a remote machine. kisui-terminal puts the folder of the two at the front of `PATH` after zsh, bash and fish have read their startup files, so they come before the `pbcopy` of macOS and work the same from a script. Your startup files are not changed. Other shells only get the folder at the front of `PATH`, so the `pbcopy` of macOS can come first when a startup file rebuilds `PATH`.

kisui-terminal keeps a history of the text copied to the clipboard of the computer it runs on: copies made in kisui-terminal and copies made in other apps (a browser, say). It keeps the last 20 texts for 12 hours, and saves them in `clipboard-history.json`, readable only by you, in its data directory (`~/Library/Application Support/dev.mm1995tk.kisui-terminal` on macOS, `~/.local/share/dev.mm1995tk.kisui-terminal` on Linux), so they stay after you close it. Copies that a password manager marks as secret are not kept. Images are not kept.

Press `Cmd+Shift+H` (macOS) or `Ctrl+Shift+H` (Linux) to open the history as a list, newest first. Type to filter it, move with the up and down keys (or `Ctrl+J` / `Ctrl+K`), then press `Enter` to paste the selected text into the pane you were typing in, or `Shift+Enter` to put it back on the clipboard. `Esc` closes the list without doing anything.

Outside kisui-terminal (while you use another app), press `Option+Space` (macOS) or `Alt+Space` (Linux) to bring up a small window with the history. The main window of kisui-terminal stays where it is. Choose a text with the up and down keys (or `Ctrl+J` / `Ctrl+K`) and press `Enter`: it goes back on the clipboard, the window shows "Copied" for a moment, then closes and you are back in the app you were using, so press `Cmd+V` (`Ctrl+V` on Linux) to paste it. kisui-terminal does not paste for you, so it needs no Accessibility permission on macOS. `Esc` closes the window without doing anything and takes you back to that app. This works only while kisui-terminal is running. On Linux, the key does not arrive when the window manager takes `Alt+Space` first (the window menu of GNOME or KDE, for example); unbind it there. In a Wayland session the key may not be caught at all (it may arrive only while an X11 app has the focus).

`kisui pane split --right` / `--down` / `--left` / `--up` splits the pane you type it in, to the right, down, left or up, and gives the new pane the focus. A command after it runs in the new pane instead of a shell (`kisui pane split --down htop`). The pane closes when the command ends, so to keep the output of a short command, run a shell that runs it, such as `kisui pane split --down sh -c "ls; exec sh"`. It refuses when the pane would be left smaller than 20 columns (`--right`, `--left`) or 5 rows (`--down`, `--up`), the same as splitting with the keys. `kisui pane title <name>` puts a name on a thin band above the pane (an empty name takes it away). The server keeps the name, so it stays when you reopen the window. A name is unique on the machine (one `kisui serve`): a name that another pane has, of any workspace or tab, is refused, and so is a name written like a pane id (`t` and a number, such as `t3`). `--name <name>` after `kisui pane split` names the new pane (`kisui pane split --right --name dev`). `kisui pane list` lists the panes of the machine, of every workspace and tab: the id, the name, the workspace of the window the pane is in (its id, such as `gk3x9q0a7bz`, and the name shown in the sidebar), the tab, the folder (cwd) and the title the program set, with `*` on the pane you type it in. `kisui pane list --json` prints the same as JSON for a program (or an agent) to read (the workspace is `workspace`, its id, and `workspaceName`). The window tells the workspaces to the server of each machine, which remembers what it was told last, so they are listed while the window is closed too; they are missing (`-`) for a tab that no window of this version has shown yet. `kisui pane send <name|id> <text>` types the text in a pane of the machine (of any workspace or tab, among the panes these commands reach: see below), pointed at by its name or id, and presses Enter; `kisui pane keys <name|id> <key>...` presses keys there (`esc`, `ctrl+c`, `up`, `enter` and so on; `kisui pane keys --help` lists them); `kisui pane close <name|id>` closes it. The focus does not move, so an agent in one pane can start another agent in a new pane and give it instructions. When the program in the pane turned on bracketed paste (most shells and agents do), the text is sent as a paste, so a text of several lines arrives as one; a newline in the text is Enter. `send` does not wait for the program to finish. The primary pane of a tab is not closed by `kisui pane close`: it closes with its tab.

```sh
kisui pane split --right
kisui pane split --down npm run dev
kisui pane title build
kisui pane split --down --name dev npm run dev
kisui pane list --json
kisui pane send build "make test"
kisui pane keys build ctrl+c
kisui pane close dev
kisui pane open --workspace review --name reviewer -- claude
```

`kisui pane read <name|id>` prints the text on the screen of a pane of the machine (of any workspace or tab, among the panes these commands reach: see below), pointed at by its name or id, so that an agent in one pane can see what an agent or a command in another pane shows. `--lines <n>` also prints n lines of the scrollback above the screen (up to 5000, what the server keeps). Only the characters come out, with no colors. A line that the terminal wrapped comes out as one line, and spaces at the end of a line and the empty lines at the bottom of the screen are left out. A full-screen program (such as `shj` or `htop`) draws on a screen that has no scrollback, so there `--lines` adds nothing. When a program prints a great deal very fast (more than about 4 MB that the server has not caught up with, such as `yes`), the server drops what it could not follow, and the text has only what came after until the program draws its screen again.

`kisui pane open --workspace <workspace> [--new] --name <name> [--cwd <folder>] [-- command ...]` adds a terminal tab at the end of a workspace of the window (pointed at by the name shown in the sidebar, such as `review` or `ws2`, or by its id, the one `kisui pane list` prints), runs the command in it (a shell when there is none) and gives the pane of the tab the name, so that an agent in one pane can start another agent in a workspace of its own and then use `kisui pane send` and `kisui pane read` on it (`kisui pane open --workspace review --name reviewer -- claude`). `--new` makes a new workspace of that name. Without `--new`, it is refused when no workspace has the name, or more than one does; with `--new`, when one already has it. An id points at one workspace also when two have the same name: a value written like an id (`g` and 10 letters or digits) is looked for as an id first. So a workspace cannot be given a name written like an id (the window refuses it, and so does `--new`). The tab is on the machine of the pane you type it in, and starts in `--cwd` (the current folder by default). The focus does not move. The name follows the rules of `kisui pane title`: when another pane has it, no tab is made. The command runs in the primary pane of the tab, so when it ends, the pane stays with its output (`kisui pane close` does not close it; close the tab). When the shell of a tab opened without a command ends, the tab closes. The window owns the workspaces, so it fails, with the reason, when the window is closed.

```sh
kisui pane read build
kisui pane read t5 --lines 200
```

`kisui pane focus`, `swap`, `zoom` and `resize` do to a pane what the pane keys do, from a pane. The pane is pointed at by its name or id (`kisui pane list`), among the panes these commands reach (see below). `kisui pane focus <name|id>` shows the tab of the pane and turns the keys of the window to the pane (`kisui pane focus --last` goes back to the pane that had the keys before, in the tab of the pane you type it in: the key for the previous pane). `kisui pane swap <name|id> --right|--down|--left|--up` swaps the pane with its neighbor in that direction (the neighbor the key for moving there goes to); the keys stay in the pane they were in. `kisui pane zoom <name|id>` toggles between showing only the primary pane of the tab of the pane and showing all its panes (it works only while the primary pane runs `shj`). `kisui pane resize <name|id> --right|--down|--left|--up <n>` moves the border of the pane that faces that direction n steps that way (n is 1 to 50), a step being what one key of the resize mode moves (2 percent of the split that holds the border); a pane at the edge in that direction has no border there, so its opposite border moves that way instead (it gets smaller). `swap` and `resize` do nothing, and say so, when there is nothing to move, and are refused while the tab shows only its primary pane. `kisui pane split` stays as it is: it splits the pane you type it in. These commands take `--machine` like `send`. The window owns the focus and what is shown, so they fail, with the reason, when the window is closed. From a pane on a remote machine, `focus` turns the keys you are typing, so it works only while you allow that machine in the window (`p` in the machine dialog), or while the keys are on a terminal tab of that machine and the pane is in a terminal tab of that machine: a remote machine cannot take the keys you are typing on your computer or on another machine. `kisui pane zoom` moves the keys to the primary pane when it switches to showing only that pane in a tab that has the keys, so it is checked in the same way then. `swap` and `resize` do not move the keys.

```sh
kisui pane focus reviewer
kisui pane focus --last
kisui pane swap build --left
kisui pane zoom build
kisui pane resize build --right 5
```

**Which panes these commands reach.** `kisui pane send`, `keys`, `read`, `close`, `list`, `focus`, `swap`, `zoom` and `resize` reach the pane they are typed in, the panes that pane opened (with `kisui pane split` or `kisui pane open`), and the panes those opened in turn. They do not reach a pane you opened in the window yourself, nor a pane that another pane opened: a program in one pane cannot type into, or read the screen of, a pane where you are root or logged in to another machine. A pane that is not reached is not in `kisui pane list`, and pointing at it fails the same way as a name that no pane has. With `--machine` it is the same on the other machine: the commands reach the panes this pane opened there (`kisui pane open --machine`) and the ones opened from those. To let the commands reach every pane of a machine, write `pane_reach = "all"` in `[server]` of the config file of that machine (see the settings below).

`--machine <machine>` makes `kisui pane list`, `send`, `keys`, `close`, `read`, `open`, `focus`, `swap`, `zoom` and `resize` work on the panes of another machine: a machine of the window, pointed at by its name in `[[gui.machines]]` (the ssh destination when it has no name), or `local`, which always means the computer the window runs on. From a pane on your computer, `--machine` reaches every machine of the window (`kisui pane read --machine dev bar`). From a pane on a remote machine, it reaches another remote machine only when you allowed that for the machine in the config file of your computer: `allow_pane_to` in its `[[gui.machines]]` entry lists the names it may point at. Your own computer (`local`) cannot be allowed in the config file. You allow it in the window, for a time: in the machine dialog (the leader, then `m`), choose the machine and press `p`, type a time (`30m`, `1h`, `1h30m`; at most 8 hours) and press `Enter`; `P` ends it earlier, and it is gone when you close the window. While it is allowed, each request to open a pane on your computer (`kisui pane open --machine local`) asks you in a window that shows the whole command, the folder, the name and the workspace, with `Deny` chosen first; you allow it either for good for that pane, or so that every later `send`, `keys`, `read` and `close` on that pane (and on the panes opened from it) asks you too. The command waits for your answer for up to 90 seconds. A machine that is not allowed reaches no other machine, and the command fails with how to allow it. The server of a machine knows only its own panes, so the window, which is connected to every machine, passes the request on; it fails, with the reason, when the window is closed or the machine is not connected. With `kisui pane open --machine`, the tab is a terminal of that machine: write `--cwd` and the command as absolute paths on that machine (without `--cwd` it starts in the start folder of that machine), or open a shell and start the command with `kisui pane send`. Apart from the requests to your own computer from a remote machine, described above, kisui-terminal asks for no confirmation: what is done where is all in the arguments of the command, for the permission rules of the agent that runs it. A machine whose name is `local` (in `[[gui.machines]]`, or added in the window before this version) cannot be chosen with `--machine`; the window shows a notice to give it another name.

```sh
kisui pane list --machine dev
kisui pane open --machine dev --workspace review --name reviewer --cwd /home/me/repo
kisui pane send --machine dev reviewer claude
kisui pane read --machine dev reviewer
```

`kisui tab` works on the tabs of the window (terminal tabs, browser tabs and database tabs) from a pane, so that an agent can do what the tab keys do. `kisui tab list` prints the tabs: the id, the name, the kind (`terminal`, `browser` or `database`), the workspace (its id and name) and the machine of each; `*` marks the tab of the pane you type it in, and `shown` the tab its workspace shows now. `--workspace <name|id>` lists one workspace, and `--json` prints `{"tabs": [...]}` for a program. The other commands point at a tab by its id or by its name (`<tab>`); a name that two or more tabs have is refused, with the ids to use instead. `kisui tab rename <tab> <name>` gives the tab a name (an empty name, `""`, gives back the automatic one). `kisui tab close <tab>` closes it; a terminal tab with a running program is refused, without asking in the window, and `--force` ends the program and closes the tab. `kisui tab move <tab> --up` / `--down` moves it one place in its workspace, and `kisui tab move <tab> --workspace <name|id>` moves it to the end of another workspace, where the window goes and shows it, as the key does. `kisui tab show <tab>` shows the tab: the window goes to its workspace and turns the keys to it. These commands make no new tab: `kisui pane open` adds a terminal tab, and `kisui open <url>` a browser tab.

```sh
kisui tab list
kisui tab rename w3k2n8q1x0ab "api server"
kisui tab move "api server" --workspace review
kisui tab show "api server"
kisui tab close --force "api server"
```

**Which tabs these commands reach.** The tabs belong to the window, so `kisui tab` reaches the tabs of every workspace, whatever `pane_reach` is, and takes no `--machine`. Which machines' tabs it reaches follows the rule of `--machine`: from a pane on your computer, every tab. From a pane on a remote machine, the terminal tabs of that machine and of the machines in its `allow_pane_to`. The tabs of your own computer (its terminal tabs, and every browser tab and database tab, which count as tabs of your computer) are reached from a remote machine only while you allow that machine in the window (`p` in the machine dialog; see `--machine` above); `local` in `allow_pane_to` has no effect here either. While it is allowed, the window does not ask for each `kisui tab` command; but while a pane of your computer is set to ask every time, a remote machine may not close terminal tabs of your computer. `kisui tab show` and `kisui tab move --workspace` turn the keys of the window to the tab, so from a remote machine that you do not allow with `p`, they work only while the keys are on a terminal tab of that machine: a remote machine cannot take the keys you are typing on your computer or on another machine. A tab that is not reached is not in `kisui tab list`, and pointing at one fails as a name that no tab has does. The window does these commands, so they fail, with the reason, when the window is closed. kisui-terminal asks for no confirmation: what is done to which tab is all in the arguments of the command.

`kisui workspace` works on the workspaces of the window from a pane, so that an agent can do what the workspace keys and the workspace switcher do. A workspace groups tabs and may have none. `kisui workspace list` prints the workspaces in the order of the sidebar, with the id, the name and the number of tabs of each (also those with no tab); `*` marks the workspace of the pane you type it in, and `current` the one the window is in, and `--json` prints `{"workspaces": [...]}` for a program. The other commands point at a workspace by its id or by its name (`<workspace>`); a name that two or more workspaces have is refused, with the ids to use instead. `kisui workspace new <name>` makes a workspace with no tab, like `n` of the workspace switcher, prints its id and leaves the window where it is. `kisui workspace rename <workspace> <name>` gives it a name (an empty name, `""`, gives back the numbered one). `kisui workspace close <workspace>` closes it and all its tabs; one with a terminal tab that has a running program is refused, without asking in the window, and `--force` ends the programs and closes it. `kisui workspace move <workspace> --up` / `--down` moves it one place in the sidebar. `kisui workspace show <workspace>` shows it: the window goes there and turns the keys to the tab it shows. The switcher itself (`workspace.switch`) has no command.

```sh
kisui workspace list
kisui workspace new review
kisui workspace rename review "review 2"
kisui workspace show "review 2"
kisui workspace close --force "review 2"
```

**Which workspaces these commands reach.** A workspace can hold tabs of several machines, so what a pane reaches follows the tabs, by the rule of `kisui tab` above. A pane reaches a workspace that has a tab it reaches, and a workspace with no tab; `kisui workspace list` counts only the tabs it reaches. `kisui workspace close` closes all the tabs of the workspace, so it works only when the pane reaches all of them; and while a pane of your computer is set to ask every time, a remote machine may not close a workspace that has a terminal tab of your computer. Closing the workspace the window is in moves the keys you are typing to the next workspace, so from a remote machine that you do not allow with `p`, it works only while the keys are on a terminal tab of that machine. `kisui workspace show` turns the keys of the window to the tab the workspace shows, so from a remote machine that you do not allow with `p`, it works only while the keys are on a terminal tab of that machine and the workspace shows a terminal tab of that machine: a remote machine cannot take the keys you are typing on your computer or on another machine. A workspace that is not reached is not in `kisui workspace list`, and pointing at one fails as a name that no workspace has does. The window does these commands, so they fail, with the reason, when the window is closed. kisui-terminal asks for no confirmation: what is done to which workspace is all in the arguments of the command.

`kisui browser` works on the browser tabs of the window (the built-in browser, `[gui.browser]` below) from a pane, so that an agent can do what the keys of the dialog of a browser tab do. `<tab>` is the id of a tab (`kisui tab list` prints it) or its name. `kisui browser new [--private] [<url>]` adds a browser tab (a private one with `--private`) to the workspace of the pane, at the new tab page or at a URL, and prints its id. `kisui browser url <tab> <url>` opens a URL (only `http` and `https`), `back`, `forward`, `reload` and `stop` do what their keys do (refused, with the reason, when there is nothing to go back to and so on, as the dialog dims them), `close` and `rename` are `kisui tab close` and `kisui tab rename` for a browser tab, `external` opens the page in your default browser, `copy-url` prints the URL (it does not write the clipboard), `bookmark add <tab>` and `bookmark list [--json]` add a page to the bookmarks and list them (not those of Chrome), and `find <tab> <text>` selects the first match in the page and prints `found` or `not found`. `devtools` and `login` only open the screen where you continue: DevTools of the page, and the external browser for a login (`s` of the dialog; only for a site in `passkey_sites`, and not in a private tab). They do not read or drive the content of a page. With the built-in browser off they refuse and say so. `reload`, `find`, `devtools` and `login` need the page of the tab, which the window makes the first time it shows the tab (after kisui-terminal starts, and for a tab in another workspace, not before); for a tab it has not shown they refuse and say so. `new` does not wait for the page to load.

```sh
id=$(kisui browser new https://example.com/docs)
kisui browser url "$id" https://example.com/changelog
kisui browser copy-url "$id"
kisui browser close "$id"
```

**Which browser tabs these commands reach.** Browser tabs are tabs of your own computer, so the rule of `kisui tab` above applies: a pane on your computer reaches them all; a pane on a remote machine reaches them (and can use `new` and `bookmark list`) only while you allow it for a time with `p` in the machine dialog. A browser tab it does not reach is not in `kisui tab list`. Even while you allow it, a command that opens a URL (`new` with a URL, `url`, `external`) or a screen for you (`devtools`, `login`), or gives something of yours back to the pane (`copy-url`, `find`, `bookmark list`), is refused from a remote machine while a pane of your computer is set to ask you every time.

`kisui db` lets a coding agent in a pane use the database connections of the settings (`[[db.connections]]`, below): `kisui db connections` lists them with what the agent may do on each, `kisui db schema <connection> [<table>]` lists the tables or the columns of one table, `kisui db query <connection> <sql>` runs one statement and prints its rows, and `kisui db propose <connection> <sql>` writes SQL into the input of a database tab for you to read and run. `--variant <variant>` chooses the environment of a connection with variants, and `--json` prints the result for a program. `kisui serve` of the machine of the pane connects and logs in, so the agent needs no client and sees no password. Every request is the agent's and follows the permission you gave it (`agent-permission`): with none, `kisui db query` is refused and `kisui db propose` is allowed; with `run = "read"`, the database refuses what writes. `kisui db propose` never runs anything; when the input of the tab already holds SQL, the window asks you before replacing it (`Enter` replaces, `Esc` keeps yours, and the command then fails). The commands do not ask for a password: it must be in the keychain or in `~/.pgpass` / `~/.my.cnf` (or already typed in a database tab of a window that is still open). What the agent runs is kept in the SQL history of the connection, marked "agent". The details are in [docs/database.md](docs/database.md#for-a-coding-agent-the-kisui-db-commands).

```sh
kisui db connections
```

kisui-terminal reads its settings from two files in its own folder, `config.toml` and `config.local.toml`. The folder is `~/.config/kisui-terminal/` (`kisui-terminal-nightly/` for the nightly, if that folder exists; `$XDG_CONFIG_HOME` is used when it is an absolute path). `config.toml` is read first and `config.local.toml` on top of it: a setting in `config.local.toml` wins. A table such as `[server]` is merged key by key. The lists `[[gui.machines]]` and `[[db.connections]]` are merged entry by entry: machines by their ssh destination (`ssh`), database connections by their name (`name`). An entry that both files have is the one of `config.local.toml`, as a whole (the keys only the entry of `config.toml` has are not taken over); an entry that only one file has stays. The order is the one of `config.toml`, then the entries only `config.local.toml` has. So you can add a machine in `config.local.toml` and keep the ones of `config.toml`. An empty list in `config.local.toml` (`machines = []` under `[gui]`) adds nothing and removes nothing, and there is no way to remove an entry of `config.toml` from `config.local.toml`: remove it in `config.toml`. Either file may be missing. Only these two files are read; a `config.nix` is not. When kisui-terminal itself writes a setting, it writes `config.local.toml`, never `config.toml`. The settings of `shj` (`~/.config/shijimi-editor/`) are not read, `ui-language` included. With home-manager, write them in `programs.kisui-terminal.settings` (the module of this flake); it creates `config.toml`.

- `[[gui.machines]]`: the machines (they show up in the machine dialog, `m`, and their workspaces in the workspace switcher, `w`) (`ssh = "dev-vm"`, `name = "dev"`). The name is also what `kisui pane --machine` points at; `local` is reserved for the computer the window runs on. A machine you add, rename or remove in the window (the machine dialog, `m`) is written to `[[gui.machines]]` of `config.local.toml`, so the window and your dotfiles keep machines in the same place. The machines that an earlier version kept in the window's own storage move to `config.local.toml` the first time this version starts.
  - `start_dir` and `shell`: the folder a new terminal of that machine starts in, and its shell (`start_dir = "~/work"`, `shell = "/usr/bin/fish"`). The settings file of the remote machine is not touched: the settings of your computer decide. Both are paths on that machine: an absolute path, or one that starts with `~` (the home folder of that machine). `shell` is the path of the shell's file alone; arguments cannot be written (nor a bare name such as `bash`; it is not looked up in `PATH`). A path on a remote machine cannot be checked from your computer, so only its form is checked when the settings are read, and `kisui serve` on that machine checks that it exists when it starts a terminal: when the folder of `start_dir` is not there, the terminal starts by that machine's own setting (`[server] start_dir` below, or its home folder). When `shell` is not a file that can be run, no other shell is used in its place: the terminal is not made, and the reason is shown (the `[server] shell` of Local is the exception: see below). A machine with neither works as before (its own `[server] start_dir` and `[server] shell`, or its home folder and `$SHELL`). A folder that is given explicitly (a new tab that takes over the folder of the current tab, `kisui pane open --cwd`) wins. A change is used from the next terminal you open, without stopping `kisui serve` (the window reads the settings again each time it makes a terminal). In a terminal started with the shell of the settings, the environment variable `SHELL` is that shell too. In the window, enter them with `t` in the machine dialog (`m`). While `kisui serve` on that machine is older than this feature, nothing is passed to it (terminals start as before).
  - `allow_pane_to` (a list of machine names; for example `allow_pane_to = ["build"]`): the remote machines that the panes of this machine may reach with `kisui pane --machine`. Leave it out, and this machine reaches no other machine. Each direction is written on its own: allowing `dev` to reach `build` does not allow `build` to reach `dev`. A machine that may reach another can run commands there, so write a name only for a machine you trust that much. `local` (your own computer) has no effect here, and the window shows a notice when it is written: a permission in a file stays after you forgot you wrote it, so working on panes of your computer is allowed only in the window, for a time (`p` in the machine dialog; see `--machine` above). The window does not write this key: a machine you add in the window reaches no other machine until you write `allow_pane_to` in its entry by hand, and the key stays when you rename the machine in the window. When the same machine is in both files, the entry of `config.local.toml` replaces the one of `config.toml` as a whole, so write `allow_pane_to` in the entry that is used. A name that no machine has allows nothing, and the window shows a notice. The window reads the list when it starts.
- `[gui.browser]`: `enabled = true` turns on the built-in browser (off by default; with it off nothing changes). Each workspace can then have browser tabs: they are listed under the workspace in the sidebar together with its terminal tabs, in the order they were opened, and choosing a tab makes it fill the whole area of the panes (choosing the workspace shows what it showed last). A tab you name shows that name in place of the page title. The page is the WebView of your OS (WKWebView on macOS, WebKitGTK on Linux), so DRM videos do not work in it, and passkeys work only through your external browser (see `passkey_sites` below); `e` in the dialog of `a` after the leader opens the page in your default browser. The leader and its shortcuts work even while the page has the focus; the other keys go to the page. The tabs and their logins (cookies) are shared by all tabs, kept on disk, and come back when kisui-terminal starts again: the tabs in `browser-tabs.json` in the data folder (`~/Library/Application Support/dev.mm1995tk.kisui-terminal` on macOS, `~/.local/share/dev.mm1995tk.kisui-terminal` on Linux), the logins in `browser/` there on Linux and in the WebView's own store on macOS. Bookmarks (`b` in the dialog of `a` after the leader, listed with `B` there) are shared by all workspaces and kept in `browser-bookmarks.json` in the same folder. The bookmarks of your Chrome (the `Default` profile: `~/Library/Application Support/Google/Chrome/Default/Bookmarks` on macOS, `~/.config/google-chrome/Default/Bookmarks` on Linux) are read, never written, and shown after yours (marked `Chrome`) on the new tab page and in the list, nested in folders as in Chrome (the bookmarks bar, other bookmarks and mobile bookmarks are the roots and start open, the folders under them start closed; select a folder and press `Enter`, or click it, to open or close it; filtering shows only the matching bookmarks with their folders open); they are read again each time the page or the list opens, and `Ctrl+D` does not delete them. Without Chrome nothing is shown and there is no error. Closing a workspace closes its tabs. A private tab (the leader, then `n`, then `B`) is different: it has its own logins, kept only in memory, so it sees neither the shared logins nor those of other private tabs; they are gone when you close it, and the tab does not come back when kisui-terminal starts again (the sidebar marks it `シークレット`). A private tab does not use `passkey_sites` below; passwords and authenticator codes work. A link or script that opens a new window (`target="_blank"`, `window.open`) opens it as a new tab of the same workspace, with the same logins as the page that opened it and still connected to it (`window.opener`), so "Sign in with GitHub" pop-ups can hand the result back; when the page closes itself, the tab closes and the page that opened it comes back. Downloads are saved to your Downloads folder (`~/Downloads`) without asking (`name (1).ext` when the name is taken); a notice tells you, and you can open the file or show its folder from it (`i o` and `i f` in the leader). With the built-in browser on, `kisui open <url>`, a URL that `shj` asks to open, and `cmd + click` on a URL in a terminal open in a new tab of that workspace. A `localhost` URL from a remote (ssh) machine opens there through the same relay as below; the URL field shows the original URL (`http://localhost:3000/`), not the relayed one.
- `[gui.browser]` `passkey_sites` (with `enabled = true`): the sites (hosts such as `github.com`) where you log in with a passkey of iCloud Keychain or 1Password, for example `passkey_sites = ["github.com", "dash.cloudflare.com", ".google.com"]`. A host matches only that exact host (`github.com` does not match `gist.github.com`). With a leading `.`, `.google.com` matches `google.com` and all its subdomains; use it for a site that moves to another subdomain after the login (Google moves from `accounts.google.com` to `myaccount.google.com`). A public suffix (a name under which anyone can have a subdomain, such as `.com`, `.co.jp` or `.github.io`) cannot be written this way, because the cookies of other people's sites would be copied too: such an entry is not used, and a notice says why (the other entries work). The WebView cannot use those passkeys, so when a page of one of these sites asks for a passkey, kisui-terminal opens the same URL in Firefox. Log in there; the kisui-terminal extension of Firefox then sends the cookies of the site back, and kisui-terminal puts them into the built-in browser and reloads the tab, logged in. Only the sites in the list move to the external browser, and kisui-terminal takes cookies only for a site it moved to, once, within 10 minutes. When you are already logged in to the site in Firefox, or log in there with a password, the extension also sends the login back by itself once the tab moves from the page kisui-terminal opened to a page of the site that does not look like a step of the login (a login, two-factor or confirmation page). When it does not come back by itself (the page stays at the same URL, or the site still asks for steps after the passkey), finish the steps and press the extension's button to send the login back by hand. To log in with a password from the external browser (for example with the 1Password extension), or on a site that stops the WebView before it asks for a passkey, open a page of the site and press the leader, `a`, then `s`: kisui-terminal opens the same URL in the external browser and waits for the site in the same way; after you log in there, it comes back by itself once the page moves on as above, or press the extension's button (not in a private tab). Install the Firefox extension from [addons.mozilla.org](https://addons.mozilla.org/addon/kisui-terminal-passkey-login/). Then restart kisui-terminal after changing the list: on each start it registers its native messaging host for the Firefox you use. Passwords and authenticator codes work in the built-in browser without moving. It does not work for sites that keep the login in localStorage, and an operation that asks for the passkey on its own screen has to be done in the external browser (GitHub remembers a confirmation for a while, so you can go on in the built-in browser after confirming there). Whether a Google login copied from Firefox keeps working in the built-in browser has not been checked: Chrome on Windows supports Device Bound Session Credentials, which bind a login to the device (macOS to follow), and we have not confirmed whether Google uses it for a login made in Firefox. So `.google.com` is a way to try, not a promise. The details are in [docs/passkey-extension.md](docs/passkey-extension.md).
- `[gui.browser]` on macOS 14 or later: the built-in browser goes through a proxy that kisui-terminal runs on your Mac (it listens only on `127.0.0.1`). The proxy looks up the addresses of sites itself and connects over IPv6 first, so Google does not move you to the site of another country (such as `www.google.com.hk`) when you use Cloudflare WARP on a network without IPv6, and HTTP/3 keeps working. All sites go through it, private tabs and pop-up tabs too; `localhost` and `127.0.0.1` (the remote `localhost` relayed below) do not. For this, the first time you open a tab of the built-in browser, kisui-terminal makes a key and a certificate for `localhost` for this Mac only, and macOS asks for your password to trust the certificate in your login keychain, only for SSL and only for the name `localhost` (it is not a CA certificate). If you cancel, the built-in browser works as before, without the proxy, kisui-terminal removes the certificate and key it made, and it does not ask again (delete `browser-proxy-declined` in the data folder to be asked on the next start). The key is kept in your login keychain, not in a file; after kisui-terminal updates, macOS may ask whether the new version may use it ("Always Allow" stops that for the version). The certificate lasts a year; a month before it runs out, kisui-terminal makes a new one, asks again, and removes the old one (if you cancel then, it keeps using the old one until it runs out, and does not ask again). To stop trusting the certificate and delete it and its key, quit kisui-terminal and run these commands (macOS asks for your password). kisui-terminal asks again the next time you open a tab; cancel it to keep the proxy off.

  ```sh
  # keep a copy of the certificate, to check afterwards
  security find-certificate -c "kisui-terminal browser proxy" -p > /tmp/kisui-browser-proxy.pem
  # delete every certificate of that name with its trust, then the key
  for h in $(security find-certificate -a -c "kisui-terminal browser proxy" -Z | awk '/^SHA-256 hash:/ {print $3}'); do
    security delete-certificate -t -Z "$h"
  done
  security delete-generic-password -s "kisui-terminal browser proxy"
  # this now fails (CSSMERR_TP_NOT_TRUSTED): the certificate is not trusted any more
  security verify-cert -c /tmp/kisui-browser-proxy.pem -p ssl -s localhost
  rm /tmp/kisui-browser-proxy.pem
  ```

- `[gui.sidebar]` `tabs-height`: while `shj` runs, the sidebar under its header is split into three sections: the tabs, the file tree and CHANGES, and each one scrolls on its own. This is the most the tabs section may take, as a percentage (an integer from 10 to 90) of the height of the sidebar (`tabs-height = 40` by default); it shrinks to fit when there are few tabs, and scrolls when there are more. You can also drag the border between the tabs and the file tree, or move it in the resize mode (`Cmd+R` / `Ctrl+Shift+R`, then `Tab` to pick it and `j` `k`); a double click (or `=` in the resize mode) puts it back to this value, and the size you set is kept after a restart. When `shj` is not running, the tabs use the whole sidebar. Adding a tab, or switching to one, scrolls the tabs section to it.
- `[gui.shortcuts]`: add your own one-press keys (shortcuts that skip the leader), by writing `"key" = "command"`, for example `"Ctrl+Alt+N" = "workspace.new"` or `"Alt+J" = "pane.focus:down"`. A key is modifiers joined by `+` (`Cmd`, `Ctrl`, `Shift`, `Alt`; at least one of `Cmd`, `Ctrl`, `Alt`) and one key, written for the OS you run on. A command is the name of an action in the leader tree (`pane.focus:left`, `pane.split:right`, `workspace.new`, `workspace.nth:0` for the first workspace, `scale:in`, `clipboard.history`, and so on; the list is in [docs/key-design.md](docs/key-design.md) section 4.3). Your key wins over a built-in shortcut on the same key; `"Cmd+D" = "none"` just turns the built-in one off. The leader keys do not change. Your shortcuts show in the list of all keys (`?` after the leader). A key that cannot be read, an unknown command, or a key written twice is reported in a notice at the bottom right, and only that shortcut is skipped. The key of `config.local.toml` wins over the same key of `config.toml`.
- A URL on the screen (underlined) opens on `cmd + click` or `cmd + shift + click` (`ctrl + click` or `ctrl + shift + click` outside macOS): in a new tab of the workspace when the built-in browser is on, otherwise in your OS default browser. `cmd + option + click` (`ctrl + alt + click` outside macOS; adding `shift` works too) always opens it in your OS default browser. Only http and https URLs open. For a `localhost` URL shown in a terminal on a remote (ssh) machine, kisui-terminal relays the port over ssh (`kisui relay`) and opens a local address, because your own browser would reach your own localhost. If nothing listens on that port, it says so instead of opening the browser. While an app has mouse reporting on (vim, tmux, htop, `shj`), a plain `cmd + click` goes to the app; use `cmd + shift + click` (or `cmd + option + shift + click`). The `url_open` setting under `[gui]` from older versions is ignored.
- `[server]`: `idle_stop_days` (days `kisui serve` stays up with no window connected; default 7, 0 = never), `pane_reach` (`"own"`, the default, or `"all"`: which panes of this machine the `kisui pane` commands typed in a pane reach; `"own"` is the pane itself and the panes opened from it, `"all"` is every pane of the machine; `kisui serve` reads it each time it is used, so a change works without stopping it), `start_dir` (the folder a new workspace's shell starts in; the absolute path of a folder that exists, or a path that starts with `~`) and `shell` (the shell of a new terminal; the absolute path of the shell's file, or a path that starts with `~/`; arguments cannot be written; `$SHELL` when it is not written, and `/bin/sh` when that is not set either). When the file of `shell` is not there or cannot be run, `kisui serve` still starts, and starts terminals with `$SHELL` instead; it writes a warning to its log (`~/.local/state/shijimi-editor/serve.log`, or under `$XDG_STATE_HOME`), once for each such path. A `shell` that is not such a path (a bare name such as `bash`) is a mistake of the settings, and `kisui serve` does not start with it. `kisui serve` reads `start_dir` and `shell` again each time it starts a terminal, so a change (removing them too) is used from the next terminal without stopping it; while the settings have a mistake, it keeps the last ones it could read. `idle_stop_days` is read when `kisui serve` starts. The `start_dir` and `shell` of `[server]` on your computer are also the terminal settings of Local: the window reads them again each time it makes a terminal and passes them to the local `kisui serve`, so a change is used from the next terminal without stopping `kisui serve` (you can also enter them with `t` in the machine dialog, `m`; they are written to `config.local.toml`). For a remote machine, write `start_dir` and `shell` in its entry of `[[gui.machines]]` on your computer (above).
- `[[db.connections]]`: the databases (MySQL and PostgreSQL) that `kisui serve` can connect to and run SQL on: `name`, `kind` (`"postgres"` or `"mysql"`), `host`, `port`, `user`, `database`, `read-only = true` to make the database refuse anything that writes, and `tls` (`"prefer"` by default; `"verify"` checks the certificate of the database, with your own certificate authority in `tls-ca`). One connection can have variants for its environments (`[[db.connections.variants]]`: `local`, `dev`, `prod`, each with its own `host`, `port`, `user`, `database` and `read-only`; what a variant does not write comes from the connection). `[db.permissions.<name>]` defines a permission (`run`: `"none"`, `"read"` or `"free"`; `propose`: whether a coding agent may write SQL into the input of a database tab; `agent-user`: the database user a coding agent logs in as), and a connection or a variant names one for you (`human-permission`) and one for a coding agent (`agent-permission`): for example free on `local`, read only on `prod`. Without them a connection works as before for you, and a coding agent runs nothing (a coding agent uses them with the `kisui db` commands, above). A permission can say that it may be elevated for a time (`elevate-to`: the permission to use meanwhile, `elevate-max`: the longest time at once, such as `"30m"`), for a connection you only read every day and sometimes have to write to. Write them on the machine that should connect (on a remote machine, in its own `config.toml`). You can also add, edit and remove the connections of this PC from the dialog that lists the connections (`a`, `e`, `d`; it writes `config.local.toml`, never a password; see [docs/database.md](docs/database.md)). A password is never written here: it comes from the keychain (macOS), from `~/.pgpass` or `~/.my.cnf`, or you type it when asked. The statements you run are kept for each connection (and each variant) on that machine. The details are in [docs/database.md](docs/database.md). You use them in a database tab (below).
- `ui-language`: the language of kisui-terminal's text, both the window and `kisui` (`en` or `ja`; English when it is not set or not one of these). The window reads it once at startup, so a change shows after the next start. It is set apart from the `ui-language` of `shj`.

**Database tabs.** A workspace can have database tabs next to its terminal and browser tabs, each a MySQL or PostgreSQL client on one of the connections above. Press `n` after the leader and choose the database with `d` (or choose "Database" in the + menu of a workspace in the sidebar): kisui-terminal asks `kisui serve` on every machine it is connected to for its `[[db.connections]]` and lists them all in one dialog, with the machine of each on the right (with none, it says "No connections"). A connection with variants has one row for each variant, shown as `name (variant)`: you choose the environment here, once, and the tab stays on it. The tab you open is listed in the sidebar like the other tabs, and `kisui serve` on the machine where the connection is written is the one that connects, so a connection on a remote machine works over ssh with no tunnel. In the tab, type SQL at the top and press `Cmd+Enter` (macOS) or `Ctrl+Enter` (Linux) to run the part you selected, or, with nothing selected, the one statement the cursor is in (statements are separated by `;`, except inside strings, comments and `$$`; a selection of two or more statements runs them one after another, each committed by itself, not as one transaction, and stops at the first that fails); the result shows as a table below, with the number of rows and the time it took under it (NULL is shown in grey italics, and a long value is cut; point at it to see all of it). Results live in result tabs, in a row above the result: running replaces the result tab that is shown (a tab is added when there is none), and `Cmd+Option+Enter` (macOS) or `Ctrl+Shift+Enter` (Linux) runs into a new result tab, so the earlier result stays. When you run two or more statements, the first replaces the tab that is shown and each of the others gets a new tab. Switch result tabs by clicking one, with `[` `]` while the result has focus, or by selecting one in the dialog of `a` after the leader (`j` `k`, then `Enter`), and close one with its × or `x` in that dialog. Each tab keeps its own page and sorting. There are at most 20 result tabs; beyond that, the leftmost ones are closed. In the table, click a cell to select it, extend with Shift+click or by dragging, and press `Cmd+C` / `Ctrl+C` to copy it (two or more cells are copied as TSV). When a `SELECT` gives more rows than one page (1000), "Previous" and "Next" under the table (or `f` and `b` in the dialog of `a` after the leader) run it again for the other pages (see [docs/database.md](docs/database.md#what-a-statement-does); add an `ORDER BY` so that the pages keep one order). Click a column heading (or press `s` with a cell of the column selected) to have the database sort all the rows by that column: ascending, then descending, then back to the original order (the SELECT is run again wrapped in an `ORDER BY`, so the pages follow the same order). `Esc` cancels SQL that is still running. In the sidebar, in the place of the file tree, is a tree of the schemas and tables (and views) of the connection while a database tab is shown (it goes back to the file tree when you move to another tab; `t` in the dialog of `a` after the leader moves the keys into it and `Esc` takes them back to the SQL box, and `r` in that dialog reloads it). Type in the box above the tree, or press `/` in the tree to move there, to keep only the tables in the tree whose name contains what you typed (capital or small letters alike); when all schemas are shown, the schemas that have a match are shown open, and `Enter`, `Esc` or `↓` takes the keys back to the tree; choose a table in it (click it, or `j` `k` and `Enter`) to run `SELECT * … LIMIT 100` on it in the preview tab of the results (the SQL box is not changed, so your draft stays). The preview tab is in italics with a dashed border, and there is only one: choosing another table replaces it. Sorting by a column, changing the page, double-clicking the tab, or running from the SQL box over it makes it an ordinary tab that stays (a run from the SQL box also ends its table switch) (in that result tab, a switch between "Data" and "Structure" then shows above the result: "Structure", or `s` in the dialog of `a` after the leader, shows the columns of the table with their types, whether they take NULL and their defaults, its indexes and its foreign keys; running SQL from the SQL box goes back to "Data"). Above the tree, the default schema of the connection is shown; click it (or press `s` in the tree) to open a list of the schemas in its place, where you type to filter and press `Enter` (it starts on the default schema of the database): a table you name without a schema is then looked for in that schema first (PostgreSQL puts it at the head of the `search_path`, MySQL runs `USE`, before every statement), and the tree lists the tables of that schema only; while you filter by name, the tables of the other schemas that match are listed after them, as `schema.table`. The schema is kept for the connection: every tab of the same connection uses it, and it is still there when you reopen kisui-terminal. To take the result out, press `a` after the leader and then `e`: choose CSV, TSV or JSON, and the clipboard or a file (a save dialog asks where; nothing is saved by itself). NULL is an empty cell (an empty string is `""`), and a value with a comma, a quote or a line break is quoted. To use an earlier SQL again, press `a` after the leader and then `h`: the dialog lists the SQL run on this connection (newest first, kept on the machine where `kisui serve` runs, up to 1000 per connection; type to filter) and putting one in the SQL box does not run it. When the database needs a password that is not in the keychain or in `~/.pgpass` / `~/.my.cnf`, or refuses the one found there, the window asks for it and sends it with that request; it is never written to a file (one that worked is kept in memory until you close the window, by the window and by `kisui serve`, and is used before the one found; `kisui serve` forgets it when the window is no longer connected). When you reopen kisui-terminal, the database tabs come back with the SQL you were writing, but not the result tabs (run it again). The tabs cannot change the data in the table cells; write the SQL for that. A coding agent can write SQL into the input of a database tab with `kisui db propose` (above): it is not run until you run it, and when the input already holds SQL the window asks before replacing it. To make a permission of the connection stronger for a time (yours or the coding agent's, where the settings allow it with `elevate-to` and `elevate-max`), press `a` after the leader on the database tab, then `p`, choose the permission and type the time (`30m`, `1h`); the tab shows what is elevated and the time left, and the permission goes back when the time is over (or when `kisui serve` stops). `P` in the same dialog ends it before that. Only you can elevate: a coding agent has no command for it.

**Proxy.** You can look at the HTTP and HTTPS of a tab, edit a request and send it again, and hold a request on its way to change it, the way you would with Burp or Caido. Show a terminal tab or a browser tab and press `x` `p` after the leader: the area splits, and a panel on the right lists the exchanges of that tab and shows the request and the response (headers and body) of the one you select (`j` `k` to select, `Tab` to switch between the request and the response, `Esc` to go back to the tab, `q` to close the panel). Only the tabs you choose go through the proxy; nothing does by default.

- The proxy runs in `kisui serve`. A terminal tab uses the `kisui serve` of its own machine (for a tab on an ssh machine, the proxy runs there); a browser tab uses the one on your computer. It listens only on `127.0.0.1`, on a port of its own for each tab. It asks for no password, so on a machine that other people use too, another user of that machine can send traffic through the proxy while it runs, and that traffic shows up in the panel with yours.
- A terminal tab: the panes you open **after** this (a split, for example) get `HTTPS_PROXY`, `HTTP_PROXY` and the variables that make programs trust the certificate authority of the proxy (`SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO`, `NODE_EXTRA_CA_CERTS` and a few more). The panes that were already open do not change (the environment of a running shell cannot be changed), and a program that does not read these variables does not go through the proxy. A program that reads the proxy variables but not the ones for the certificate authority fails with a certificate error instead: for example Go programs on macOS (`gh`, `terraform`; Go on macOS checks certificates with the keychain and does not read `SSL_CERT_FILE`) and Java programs. To use such a program, stop the proxy for the tab (`x` `s`) and open a new pane.
- A browser tab: its page is loaded again through the proxy, with data (cookies, logins) of its own that is not kept on disk, like a private tab. The WebView of the OS sets a proxy for a set of data, not for one tab, so a tab that shares the logins of the other tabs cannot go through the proxy alone. Log in again inside the tab if you need to. In such a tab the WebView does not check certificates itself: all its connections go to the proxy on `127.0.0.1`, and the proxy checks the certificate of the real site. On macOS this needs macOS 14 or later.
- To read HTTPS, the proxy makes certificates with a certificate authority of its own. `kisui` makes one for each machine the first time and keeps it in the folder of its state (`~/.local/state/shijimi-editor/proxy-ca-key.pem`, readable only by you; `proxy-ca.pem` is the certificate). It is **not** installed in the OS: only the panes and tabs you send through the proxy trust it. The proxy checks the certificate of the real site itself and answers 502 when it is wrong.
- To edit and resend: select an exchange in the panel and press `e`. The lower part of the panel becomes a form with its request (method, URL, headers and body). `Cmd+Enter` on macOS or `Ctrl+Enter` on Linux sends it and `Esc` cancels. The proxy (`kisui serve`) sends it, and the request and its response show up as a new row of the list (marked `↻`); the page and the shell do not get the response. `Host` comes from the URL and `Content-Length` from the body. A body that is not text, and a compressed body, are sent as they were. A body that was cut at the limit of the record cannot be sent as it was, so the body you write is sent.
- To hold requests on their way: press `i` in the panel (or `x` `i` after the leader). While it is on, each request of the tab stops before it is sent and shows up in the list as held (its status is `||`), and the page or the program waits. Select a held request and press `f` to forward it as it is, `e` to edit it (`Cmd+Enter` or `Ctrl+Enter` then forwards what you wrote in its place) or `d` to drop it (it is not sent, and the page or the program gets 502). After each one, the oldest held request is selected, so you can go through them in order. Press `i` again to stop holding: the held requests go on as they are. Closing the panel, stopping the proxy for a terminal tab (`x` `s`) and closing the window also stop holding and let the held requests go on, so that nothing keeps waiting where you cannot see it. Stopping the proxy for a browser tab, and closing a tab, cut the held requests instead (they are not sent; a browser tab loads its page again without the proxy). Only requests are held, not responses, and holding is off for every tab until you turn it on. The proxy does not give up on a held request by itself; if the page or the program stops waiting, the row becomes failed (a request over HTTP/1.1 whose body was not read stays held until you forward or drop it). A body is shown and can be edited when its size is known and at most 256 KiB; otherwise it is forwarded as it is.
- Closing the panel (`x` `c`) keeps the tab on the proxy and keeps recording (up to 1000 exchanges for a tab, and the first 256 KiB of each body). `x` `s` stops: new panes of a terminal tab no longer get the variables (the proxy keeps relaying, without reading, for the panes that still have them), and a browser tab is loaded again without the proxy.

`kisui proxy` runs the same proxy by itself, without the window. It prints the `export` lines to paste into another terminal, then a line for each exchange (`-v` adds the headers and the bodies; `--listen 127.0.0.1:8080` chooses the address):

```sh
kisui proxy
kisui proxy -v --listen 127.0.0.1:8080
```

**Mascot (experimental).** A character can push the leader guide from the left edge of the terminal to its place at the bottom right. No character ships with kisui-terminal. Each character is a folder `mascot/<name>/` next to `config.toml` (`~/.config/kisui-terminal/mascot/<name>/`; `kisui-terminal-nightly/mascot/` for the nightly, if that folder exists; `$XDG_CONFIG_HOME` is used when it is an absolute path) on the machine where the window runs, holding a `mascot.toml` and transparent PNG images facing right. Choose the character in the leader: `c` `s` lists the folders in `mascot/` and writes your pick to `config.local.toml` (never to `config.toml`, which may be a read-only file placed by home-manager), and `c` `r` reloads the character you use, so a replaced image shows without restarting the window (from the next time the leader opens). You can also write the name yourself with `mascot = "<name>"` under `[gui]`; with no name, no character appears. To hand out a character, ship a script that unzips it into `mascot/<name>/`; run it in a kisui-terminal terminal, then press `c` `r` (or `c` `s` for a new character). kisui-terminal never runs the script. `mascot.toml` lists, scene by scene, the image files of the frames (any names, any number of frames), how long each frame shows (default 200 ms), whether the frames repeat, and how fast it moves (default 90 px per second). It carries the guide, takes a breath when it arrives, after a while (3 seconds by default) picks a rest at random (drinking coffee, sitting in a chair, and so on), and when you close the guide with Esc it pushes the guide to the right, off the screen (a `[push]` scene sets its frames and speed; without one it uses the frames of the carrying scene at the default 90 px per second). Any other way of closing (the leader key again, running an action, a key that is not listed, the window losing focus) plays a goodbye in place and disappears (or disappears at once if the guide opened a dialog, or has no goodbye). The format, every scene, the defaults, and how to hand out a character are in [docs/mascot.md](docs/mascot.md). The fixed names of earlier versions (`walk-1.png` to `walk-4.png`, `stop.png`) are no longer read. The files are read when the window starts and when you press `c` `s` or `c` `r` in the leader. When the OS setting "reduce motion" is on, the character stands still at the bottom right and disappears at once when the guide closes, even with Esc. If you close the guide with Esc while the character is still carrying it, it does not push; the character and the guide disappear at once. Keys after the leader work at once, without waiting for the animation.

To make a character, a skill `make-mascot` writes the `mascot.toml` and one prompt per frame image (it does not make the images; make them with any image generator you like). It is a plugin `kisui-mascot` for coding agents. Claude Code: `/plugin marketplace add mm1995tk/kisui-terminal`, then `/plugin install kisui-mascot --marketplace mm1995tk/kisui-terminal`. Codex: `codex plugin marketplace add mm1995tk/kisui-terminal`, then `codex plugin add kisui-mascot@kisui-terminal`.

On a remote machine (ssh), kisui-terminal installs its own `kisui` and `shj` under `~/.cache/kisui-terminal/<version>/` after asking you; it does not touch the `shj` on the PATH there.

### Keys

You do not have to remember the keys. Press the leader, `Cmd+K` (macOS) or `Ctrl+Shift+K` (Linux), and the keys you can press next appear at the bottom right of the window (over the notice cards, which are there too), each with what it does. ## Development

Use the Nix devShell (Go, gopls, gomod2nix, git, Node.js, Rust, and on Linux the WebView libraries). With direnv, `.envrc` enters it automatically. Every command runs from the root of the repository: `go.mod` (`kisui`, the server), `package.json` (the web UI, sources in `app/`) and `Cargo.toml` (a workspace whose member is the Tauri shell, `app/src-tauri`) are all there.

```sh
nix develop
npm ci                 # the web UI (once, and after package-lock.json changes)
go test ./...          # kisui
npm test               # the web UI
cargo test             # the Tauri shell
go build -o target/dev/kisui ./cmd/kisui   # the kisui the window starts (SHIJIMI_KISUI)
SHIJIMI_KISUI=$PWD/target/dev/kisui npm run tauri dev   # run it (outside the devShell: nix run .#dev)
npm run storybook      # one component at a time in a browser, without Tauri (docs/design/storybook.md)
nix fmt                # format everything
nix flake check        # every check CI runs: formatting, go test, the build and its tests
```

In `tauri dev` the terminals use the `shj` on your PATH; the built app ships its own (`packaging/`).

The layout: `app/` is the window (Solid + TypeScript in `src/`, laid out as `ui/`, `features/` and `infrastructure/`: see [docs/design/frontend-structure.md](docs/design/frontend-structure.md); the Tauri shell in `src-tauri/`), `cmd/kisui` and `server/`, `attach/`, `rpc/`, `config/` are `kisui` (Go), `internal/` is what kisui keeps of the agreement with `shj` (`ctl`), the PTY (`term`), the build (`buildinfo`) and its messages (`i18n`). `docs/design/` is the design history.

Releases are described in [docs/releasing.md](docs/releasing.md).
