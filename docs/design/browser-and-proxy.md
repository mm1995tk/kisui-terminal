# ブラウザの埋め込みと Web プロキシ（設計）

Issue #15 の検討結果。方式を決め、実装は個別の Issue に分ける。

> **内蔵ブラウザ（ブラウザタブ）は #116 で外した。** GUI にはブラウザのペインを足したが（#556）、#96 で外した（末尾の「GUI の外部ブラウザ」）。TUI に残っているのはポート転送（`:browser forward`）と外部ブラウザ連携だけ（`:open-url` と `Space o` は shijimi-editor から外した。mm1995tk/shijimi-editor#646）。理由は末尾の「内蔵ブラウザを外した理由」。**GUI の内蔵ブラウザは #202 で、ペインではなくワークスペースのタブの形で入れ直した**（末尾の「GUI の内蔵ブラウザ（#202。入れ直し）」）。この文書の他の部分は、当時の検討の記録として残す。

## 結論

- Web ページは **ヘッドレス Chromium でスクリーンショットを撮り、既存の画像ビュー（`core/image.go`、描くのは `ui/tui/image_draw.go`）で表示する**。
- 同じ仕組みを #14（mermaid プレビュー）と共有する。
- リモート環境（VM）向けに、**shijimi に組み込みの HTTP リバースプロキシ**を持つ。手元のブラウザからは SSH のポート転送（`ssh -L`）で見る。
- 外部ブラウザ連携（`xdg-open` / `open`）を、最初に作る最小の手段とする。

## 検討した方式

### 描画方式

| 方式                          | 長所                                                                  | 短所                                            | 判断                 |
| ----------------------------- | --------------------------------------------------------------------- | ----------------------------------------------- | -------------------- |
| テキスト化（w3m / lynx 風）   | 依存なし、軽い                                                        | JS を実行できない。SPA の開発サーバーは空になる | 採用しない           |
| 画像化（ヘッドレス Chromium） | JS 込みで正しく描画できる。画像ビューを再利用できる。#14 と共有できる | Chromium が必要。操作は再撮影になる             | **採用**             |
| 外部ブラウザ連携              | 実装が小さい。完全な機能                                              | 端末の外に出る。リモートでは使えない            | 最初の一手として採用 |

画像化はハーフブロック描画のため解像度が低い。読み取り用途は外部ブラウザ連携で補う。
Kitty graphics protocol による高解像度表示と動画の再生は、Chromium を常駐させる方式として別に実装した（#57、下の「ライブ表示」）。Sixel 対応は扱っていない。

### プロキシの形

- shijimi が `127.0.0.1:<ポート>` で待ち受け、`localhost:<対象ポート>` へ転送する。
- 転送先は `:browser forward <対象ポート> [待ち受けポート]` で追加する。
- リモートの VM で shijimi を動かしている場合、手元で `ssh -L <手元ポート>:127.0.0.1:<待ち受けポート> vm` を実行すると、手元のブラウザで見られる。
- 公開インターフェース（`0.0.0.0`）には既定でバインドしない。

#### 直接の `ssh -L` に対してプロキシが足すもの

`ssh -L <手元ポート>:127.0.0.1:<対象ポート> vm` と直接書けば、転送だけならプロキシ無しでできる。プロキシを持つ理由は次の 3 つ。

1. **待ち受けポートを固定できる。** 開発サーバーのポートが変わっても、`ssh -L` とブラウザビューの URL は変えずに済む。
2. **ブラウザビューの URL を一本化できる。** エディタ内のブラウザビュー（#36）は常に待ち受けポートを参照する。
3. **`::1`（IPv6）にしか bind しないサーバーを、`127.0.0.1`（IPv4）で受けられる。**

この 3 つが不要な場合は、`ssh -L` を直接使えばよい。#37 はこの範囲に絞る（転送だけの機能は作らない）。

## 後から変えられるようにする点

- ブラウザの実行ファイルのパスは設定（`config.toml` の `[browser]` の `chromium`）で上書きできるようにする。
- 描画バックエンドは `Renderer` インターフェースの裏に置く。Chromium 以外に差し替えられる。
- プロキシの待ち受けアドレスは設定で変えられるようにする。
- **設定の置き場所:** `[browser]` セクションは `~/.config/shijimi-editor/config.toml` か `.shijimi-editor/config.toml` にのみ書く。README に明記する。

## ライブ表示（Issue #57）

Kitty graphics protocol に対応した端末（Kitty / Ghostty / WezTerm）では、静止画の代わりに常駐 Chromium の画面を流す。

- **画像の配置:** Unicode placeholder（U+10EEEE + 行・列の結合文字、前景色が画像 ID）。画像データは端末へ直接送り、bubbletea が描くのはセルの文字だけにする。差分描画や、パレットなどの重ね描きと衝突しない。
- **書き込みの直列化:** bubbletea の出力（`tea.WithOutput`）と画像の送信は同じ `kitty.Writer` を通し、エスケープシーケンスが混ざらないようにする。応答が stdin に返らないよう `q=2` を付ける。
- **Chromium:** `internal/cdp` が chromedp で常駐させ、`Page.startScreencast`（JPEG、quality 70）でフレームを受け取り、Go 側でデコードして zlib 圧縮の RGB（Kitty の `f=24,o=z`）で端末へ送る。PNG は動画で 1 枚数 MB になり SSH 越しで詰まるため使わない。フレームは最新の 1 枚だけ保持し、最大 15 fps で端末へ送る。端末が遅いときは映像がコマ落ちするだけで、遅延は溜まらない。
- **表示中だけ送る:** 別のタブが前にあるときは screencast を止める。再表示で最新のフレームを送り直す。
- **入力:** マウスは、画像内の相対位置からページの座標へ変換して `Input.dispatchMouseEvent` で送る（セルのピクセルサイズに依存しない）。キーは入力モードのときだけ送る。
- **viewport:** セル数 × セルのピクセルサイズ（`TIOCGWINSZ`。取れなければ 10×20）。幅 1600 px・高さ 1000 px を上限に、比率を保って縮める。
- **戻り先:** 非対応端末では従来どおり `render.Renderer` の静止画表示。`render.Renderer` は mermaid プレビューも使うので残す。
- **sandbox:** 無効にしない（#51）。

## 内蔵ブラウザを外した理由（#116）

Chromium を shijimi と同じマシン（多くは SSH 先の VM）で動かし、画面を端末へ送る形には、次の問題があった。

- Herdr の中では、ペインの描き直しで Kitty graphics の画像が消える（#102）。半ブロックの静止画にしても、JS の読み込み前に撮れてしまう。
- SSH 越しでは動画のコマが多すぎる。実測で毎秒約 8 MB を送り、Kitty が受け取りの処理に追われて画面を描けなくなった（#103）。
- 音声は VM で鳴るので、手元まで運ぶ仕組みが別に要る（#104）。

根本から直すには、ブラウザを手元のマシンで動かし、手元に中継プログラムを置いて端末への出力に画像を混ぜる必要がある（terminal-browser の `--ssh` と同じ形）。費用に見合わないため、ブラウザ機能を外し、ポート転送と手元のブラウザで見る形に戻した。

## GUI の外部ブラウザ（#96。内蔵ブラウザのペイン #556 は外した）

GUI には #556 で、Tauri の子の webview でページを出す「ブラウザのペイン」を足したが、#96 で外した。理由は次の通り。

- 見づらく、操作感が良くない。
- パスキー（WebAuthn）が使えない（macOS の WKWebView・Linux の WebKitGTK の制約）。
- Netflix など DRM の動画が再生できない。

動画を小 Window で観るのは Safari のピクチャー・イン・ピクチャーで済ませる。ページは手元の外部ブラウザ（OS 既定のブラウザ）で開く。Chromium（CEF）を中に入れることは、しない。

- **開く入口は 3 つ**：shj の URL を開く要求（`ctl.PaneRequest` の `op: "open"`・`kind: "browser"`。shj の PR を開く操作などが使う）、`kisui open <URL>`、ターミナルの URL のクリック（`cmd + click`・`cmd + shift + click`。macOS 以外は ctrl。どちらも同じ）。内蔵ブラウザを有効にしていれば、どれもワークスペースの新しいタブで開く（#203。下の「URL を内蔵ブラウザのタブで開く」）。前の 2 つは `kisui serve` が GUI に `browser.open` を通知し（ペインは作らない。gui-protocol.md の「ブラウザの URL を開く」）、クリックは GUI の中で済む。開くのは殻の `open_url_external`（`app/src-tauri/src/open_url.rs`）で、`open`（macOS）・`xdg-open`（それ以外）に URL を渡す。
- **開いてよい URL**：http と https だけ。ユーザー名とパスワードを含むもの・制御文字を含むもの・長すぎるものは断る（`kisui serve` と殻の両方で確かめる）。
- **リモートのマシンの `localhost`**：ワークスペースのマシンが ssh の先のとき、host が `localhost`・`127.0.0.1`・`[::1]`・`0.0.0.0`・`*.localhost` の URL は、手元の外部ブラウザでそのまま開くと手元の別のマシンに行ってしまう。そこで GUI が `ssh <ホスト> -- <kisui> relay` を張り（#127。`kisui attach` と同じ起こし方で、質問は GUI の Dialog に出る askpass）、手元の `127.0.0.1:<空きポート>` で待ち受けて、ブラウザの接続を `kisui relay` の上でリモートのポートへ中継する。開くのは `http://127.0.0.1:<空きポート>/…`。`kisui relay` はマシンごとに 1 本、待ち受けはマシンと URL のポートごとに 1 つで、どちらも使い回し、GUI が終わるときに止める（ページを開いたあとも、タブが見続けられるように残す）。待ち受けのポートは、マシンとリモートのポートから決まる番号（20000〜29999。FNV-1a）を先に試し、誰かが答えるか bind できなければ空きポートにする（#203。起動し直しても同じ origin になり、ページの localStorage などが残る。Cookie はポートを区別しないので、もともと残る）。開く前に、そのポートにつながるかを確かめ、誰も待っていなければ開かずに理由を出す。ほかの host は、手元から直接開く。取り決めと Dialog の側の動きは `relay.md`。
- **`ssh -L` をやめた理由（#127）**：前は `ssh -N -L 127.0.0.1:<空きポート>:localhost:<ポート> <ホスト>` のポート転送で見せていた。`ssh -L` は、つなぎ先の sshd と途中の中継がポート転送を許すときにしか使えない（Cloudflare Zero Trust の Access for Infrastructure・`AllowTcpForwarding no` の sshd・会社の踏み台）。普通の ssh のセッションの標準入出力の上で中継する `kisui relay`（#126）に替え、ターミナルが使える環境なら URL も開けるようにした。`ssh -L` に戻す道は残していない。
- **絶対 URL の localhost**：ページの中のリンクやリダイレクトが絶対 URL の `http://localhost:…` を指すと、転送を通らない（今は対処しない）。
- **設定 `[gui] url_open`**：開き先を内蔵ブラウザか外部ブラウザかから選ぶ設定だったが、選ぶものが無くなったので外した。設定ファイルに残っていても無視し、起動を止めず、間違いとして出さない。

## GUI の内蔵ブラウザ（#202。入れ直し）

#96 で外した理由（上の「GUI の外部ブラウザ」）を、次のように解いて入れ直した。作業（ワークスペース）ごとに、ブラウザのタブを持てる。

- **見づらい**：前はペインを分けて、画面の半分にページを出していた。今は、タブを選ぶとグリッドの場所すべてがそのページになる（ペインは分けない）。#231 以降は、ターミナルのグリッドもタブの 1 つなので、Workspace band を選んでも、ターミナルのグリッドに戻らない（そのワークスペースが出していたものが出る。ターミナルのタブの行を選べば戻る）。
- **パスキー**：パスキーが要る場面だけ Firefox に移って戻る（#206・#207）。設定の `[gui.browser] passkey_sites` に書いたサイトのページがパスキーを求めると、同じ URL を外のブラウザで開き、拡張機能（#207）が送るログインした後の Cookie を内蔵ブラウザに写して、タブを開き直す。取り決めと安全のための作りは `docs/passkey-extension.md`。
- **DRM の動画**：内蔵ブラウザでは再生しない。追加の部品で再生する案は #208 で検討する。
- **CEF**：入れない。OS の WebView（Tauri の子の webview。macOS は WKWebView、Linux は WebKitGTK）を使う。

この Issue（#202）で作ったのは土台だけ。URL を開く入口（`kisui open`・shj の URL を開く要求・URL のクリックから内蔵ブラウザで開く。#203。下の「URL を内蔵ブラウザのタブで開く」）、シークレットのタブ・新しい Window・ダウンロード（#204）、ブックマークなど（#205）、パスキー（#206）は別の Issue。

- **有効にする**：GUI の設定ファイル（`$XDG_CONFIG_HOME/kisui-terminal/config.toml`。`config.local.toml` が上に重なる）に `[gui.browser]` `enabled = true` と書いた人にだけ出す。書いていなければ、リーダーの `o` のグループもサイドバーのタブも出ず、何も変わらない。
- **タブ**：タブは GUI のワークスペース（`docs/design/gui-protocol.md` の「ワークスペース」。#231）に属し、サイドバーの Workspace band の下に、ターミナルのタブと一緒に開いた順に並ぶ（サイドバーに出るのは、フォーカスしているワークスペースだけ）。どのワークスペースにも属さないタブは作らない。ワークスペースを閉じると、その下のタブも閉じる。タブには名前を付けられ（リーダーの `t` で開く Workspace switcher の `r`・サイドバーの行の鉛筆。#459 までは `o R`）、付けた名前を 1 行目に出し、ページの題は出さない（空にするとページの題に戻る）。ブラウザのタブにマシンは出さない（ページを表示するのは手元の PC）。タブは、開いたときのターミナルのタブのマシンを覚える（#203 のリモートの `localhost` の中継で使う）。
- **favicon**（#237）：サイドバーのブラウザのタブの行の頭に、ページの favicon を出す（取れないとき・読み込み中は地球のアイコン）。ページの読み込みが終わったとき・（読み込みの後に）題が変わったときに、殻がページの中で `browser_favicon.js` を動かして読む（`app/src-tauri/src/favicon.rs`）。動かすのはページの外の世界（isolated world。Linux は WebKitGTK の `call_async_javascript_function` の world、macOS は `WKContentWorld`）で、ページのスクリプトからは見えず、DOM の関数を差し替えられても効かない。殻から呼んで答えを受けるので、ページが偽の知らせを送る口は無い（キーの知らせのような `window.open` の URL は使わない。Linux の WebKitGTK は、ユーザーの操作の無い `window.open` を止めるため）。スクリプトは `<link rel="icon">`（32×32 か SVG を先に）、`apple-touch-icon`、`/favicon.ico` の順に、ページの中で読み込み、32×32 の PNG の data: URL にして返す。読み込むのはページ自身（ページと同じデータ。シークレットのタブはディスクに残さないデータ）で、殻とメインの webview はネットワークに出ない。外の origin の画像は CORS で許されたものだけ読める（許されなければ次の候補）。殻は答えの形（PNG の data: URL・base64 の文字・64 KB まで）を確かめてから画面に渡す（`browser-favicon`）。読み込みが始まったら・新しく頼んだら、それまでに頼んだ答えは捨てる（後から届いた古い答えで上書きしない）。読み込み中は頼まない（macOS では、読み込みが途中で失敗する・止められると、wry が読み込みの終わりを知らせないので、次の読み込みが終わるまで地球のアイコンのまま）。favicon は覚えない（`browser-tabs.json` に書かない。シークレットのタブの favicon をディスクに残さないため。再起動の後は、ページを読み込めばまた出る）。新しいタブのページ・ブックマークには出さない。
- **読み込み中の印と、止める操作**（#449）：URL バーの下の端に細い進み具合の線を出し（バーの中に収め、ページはずらさず、重ねもしない）、↻ を「×」に替える。殻が、OS の WebView の「読み込み中か」と進み具合（Linux は WebKitGTK の `is_loading`・`estimated_load_progress`、macOS は WKWebView の `isLoading`・`estimatedProgress`）を、遷移が始まったとき（`on_navigation`・`browser_go`・`browser_nav`・`on_page_load` の始まり）から終わるまで一定の間隔で読み、変わったときだけ `browser-loading` を送る（`app/src-tauri/src/browser_progress.rs`）。wry の `on_page_load` は macOS では最初の応答が来てからしか知らせず、つながるまで・証明書の確認の間を知らせられないので使わない。止めるのは `browser_stop`（WebView の `stopLoading`。打ち切りは失敗として知らせず、ページは前のまま残る）。ページの `Esc` は、ページのスクリプト（`browser_keys.js`）が `kisui-key://esc` で殻に知らせ（止めず、ページにも届く）、殻が `browser-escape` で画面に渡し、画面が読み込み中のタブだけ止める。Esc を常に横取りしない（読み込み中でないときの Esc は、ページのダイアログを閉じるなどに使われる）ためと、読み込み中かを覚える場所を画面の 1 か所にするため。
- **戻る先・進む先が無いときの ←・→**（#450）：URL バーの ← は戻る先が無いとき、→ は進む先が無いとき、薄くして押せない（`disabled`）。有無は殻が OS の WebView の履歴（Linux は WebKitGTK の `can_go_back`・`can_go_forward`、macOS は WKWebView の `canGoBack`・`canGoForward`）から、タブごとに 1 本のスレッドが一定の間隔（250ms）で読み（`browser_progress.rs`）、変わったときだけ `browser-history` で知らせ、画面がタブに持つ（`history`。覚えない）。ページに入れたスクリプトで `history` を数えない：OS の WebView の履歴が正で、リダイレクトや失敗の画面（#432。失敗した読み込みは履歴に入らない）も、WebView の言うとおりになる。読み込みも題の変化も伴わない `pushState` の履歴の変化にも、読む間隔の分の遅れで追いつく（タブごとに 1 本なので、読んだ順に送る）。ブラウザのタブの Dialog（リーダーの `a`。#459）は、この値で、戻る・進むの行に「戻る先がありません」などの理由を出す（設定の Shortcut の `browser.back`・`browser.forward` は、先が無いとき今までどおり何もしない）。
- **読み込みの失敗の表示**（#432）：証明書が信頼できない・期限切れ・名前が合わない・名前が引けない・つながらない・時間切れなどで、ページの読み込みが、ページが出る前に失敗すると、WebView はページを替えず、前のページが残る（macOS の WKWebView は何も知らせない。Linux の WebKitGTK は、WebKit 自前のエラーのページを出し、wry はどちらも殻に知らせない）。そこで殻が、失敗を OS の WebView から直接受ける（`app/src-tauri/src/browser_load.rs`）：macOS は `webView:didFailProvisionalNavigation:withError:` を、wry の delegate のクラスに足し（browser_capture.rs の証明書の確認の受け口と同じ手。WebKit は delegate を付けたときに受け口を調べて覚えるので、最初のタブの webview を作る前に足す。メインの画面は先に作ってあるので変わらない）、Linux は `load-failed` と、理由が詳しい `load-failed-with-tls-errors` を受ける。受けたら、タブの id・開こうとした URL・理由の分類（`cert-untrusted`・`cert-expired`・`cert-not-yet-valid`・`cert-name`・`cert-other`・`host-not-found`・`refused`・`timed-out`・`offline`・`lost`・`other`）・OS の説明の文を、`browser-load-failed` で画面に知らせる。画面（`BrowserArea.tsx`）は、そのタブのページを隠し、開こうとした URL・理由の文（日本語と英語。`browser.loadFailed.*`）・「もう一度開く」を出す。「読み込み直す」（ブラウザのタブの Dialog の `r`・Cmd+R・URL バー・「もう一度開く」）は、失敗したままのタブでは、前のページでなく、失敗の表示に出している URL を、URL バーと同じ道（`browser_go`）で開き直す（`app/src/features/browser/pages.ts` の `navPage`）。WebView は失敗した読み込みを履歴にも今の URL にも入れないので、WebView の読み込み直し（`browser_nav` の reload）では失敗の前のページを読み直してしまう。開き直す URL は、利用者が見ている失敗の表示（タブの `loadError`）だけから取る。初めは殻が失敗した URL を別に覚えて `browser_nav` の reload で開いていたが、macOS で「もう一度開く」が失敗の前のページを読み直した（#432 の macOS での確認）。殻の覚えと画面の表示は別々に決まる（画面は、知らせの URL が空ならタブの今の URL を出す。殻は空の URL では開けず、WebView の読み込み直しになる）ので、2 つがずれると、見えている URL と違うページを開く。覚えを画面の 1 つにした。殻は URL を切らずに送り（切ると別の URL を開き直す）、長い URL で画面が埋まらないようにするのは画面（`browser.css`）。macOS では、失敗の URL を `NSErrorFailingURLStringKey` が無ければ `NSErrorFailingURLKey` から取る。
  - **表示を片付ける**のは、そのタブの次の読み込みを頼んだとき（`browser_go`・`browser_nav` の reload。URL を開く・読み込み直す）と、ページが替わったとき（`browser-page` の `loading`）。殻が `browser-load-cleared` を送り、画面はそれで片付ける（殻は失敗を覚えず、頼んだ・替わったら必ず送る。画面は、失敗の表示が無ければ何もしない）。戻る・進むは、頼んだ時点では片付けない：行き先の履歴が無いと何も起きず、片付けると、開けなかった URL が URL バーに残ったまま、失敗の前のページが出てしまう（証明書を断ったサイトの URL が、別のページの上に出続ける）。履歴があれば別の項目に移るので、ページが替わった知らせで片付く。頼んだ読み込みがまた失敗すれば、表示が出直す。初めは、ページが替わった知らせだけで片付けていたが、macOS で、失敗の前に最後に開けたページと同じ URL に移ったとき、この知らせが来ず、表示が残ったままになった（#432 の macOS での確認。WKWebView がそのとき知らせない理由は確かめられていない。Linux の WebKitGTK では知らせが来る）。片付けるかを WebView の知らせだけに任せていたのが原因なので、殻が読み込みを頼んだ時点でも片付ける。同じ URL に移ったときは、知らせが来なくても片付き、WebView に残っていた前のページ（頼んだ URL のページ）が出る。
  - **証明書の確認は緩めない**：知らせるだけで、エラーを無視して開く道も、ここで作らない（`TLSErrorsPolicy::Ignore` の設定や、証明書の問い合わせへの「使う」の答えは、通すタブ（#409。browser_capture.rs）のものだけで、変わらない）。macOS は、証明書が信頼できない・名前が合わないを、OS が同じコード（`-1202`）で返すので、まとめて「信頼できない」と出す。Linux は名前が合わないを見分けて出す。
  - **macOS の期限切れ**：macOS は、期限切れの証明書（`https://expired.badssl.com/` など）でも `-1201`（`NSURLErrorServerCertificateHasBadDate`）でなく `-1202` を返す。そこで、エラーに付いてくる行き先の証明書（`NSErrorPeerCertificateChainKey` の並びか、`NSURLErrorFailingURLPeerTrustErrorKey` の SecTrust の証明書）のうち、行き先自身の証明書（並びの先頭）の有効期間（DER の validity）を殻が読み、期限切れなら「期限が切れています」、まだ有効でなければ「まだ有効ではありません」と出す。中間の証明書は見ない（サーバーが古い発行元への橋渡しの期限切れの証明書を並びに残していることがあり、本当の理由を「期限切れ」と取り違えるため）。証明書を確かめ直す（`SecTrustEvaluateWithError`）方法は、受け口が動くメインスレッドで OS（trustd）に問い合わせて待つことになるので採らなかった。有効期間を読むだけなら、OS に問い合わせず、Linux でも試験できる。
  - **プロキシに通したタブ**（#409）：行き先につながらないと（証明書が正しくない・名前が引けない・つながらないなど）、プロキシは 502 の文字だけのページを、ふつうの応答として返すので、WebView の読み込みは失敗にならない。そこでプロキシ（`proxy/failure.go`）は、その 502 に、理由の分類（上と同じ名前）を `X-Kisui-Proxy-Error` に、Go のエラーの文を `X-Kisui-Proxy-Error-Detail` に付ける。殻は、通したタブのページ（上のフレーム）の応答にこのヘッダーがあれば、ページを出さずに読み込みを打ち切り、同じく `browser-load-failed` で知らせる。Linux は `decide-policy`（応答のとき。wry の受け口は遷移のときしか答えない）で受け、macOS は wry の delegate の `webView:decidePolicyForNavigationResponse:decisionHandler:` の実装を包む（wry がこの受け口を持つので足せない。プロキシの失敗の応答のときだけ打ち切り、ほかは wry の元の実装に渡す）。打ち切った読み込みは WebKit が「遷移の打ち切り」（macOS は `WebKitErrorDomain` 102、Linux は `FrameLoadInterruptedByPolicyChange`）で知らせるが、これは失敗として知らせない。
    - ヘッダーを信じるのは通したタブだけ。プロキシは、行き先が同じ名前のヘッダーを返しても、クライアントに渡さない（`ReverseProxy` の `ModifyResponse` で消す）ので、ページが「開けなかった」画面を出させることはできない。通していないタブでは、ページが名乗れてしまうので見ない。
    - 中のフレームや、ページが読むほかのもの（画像・スクリプト）の失敗は、ページを替えないので知らせない（プロキシのパネルの一覧で見える）。ターミナルのタブのプログラムには、ヘッダーが 2 つ増えるだけで、応答は今までどおり。
  - **知らせない失敗**：打ち切り（次の遷移・`stop()`。macOS の `-999`、Linux の `Cancelled`）と、ダウンロードへの切り替え（`WebKitErrorDomain` の `102`・Linux の `FrameLoadInterruptedByPolicyChange`）は、エラーではないので、今までどおり（Linux は WebKit の既定の扱い）。読み込みがページの途中で失敗した場合（`didFailNavigation`。ページはすでに出ている）も、今までどおり。
  - **Linux は WebKit 自前のエラーのページを出させない**（`load-failed` で true を返す）。出させると、失敗のあとに前と同じ URL の読み込みがもう一度始まり、画面は失敗の表示を片付けてしまうため。macOS と同じく、前のページを残したまま画面が上に出す。Linux の WebKitGTK は、失敗のあとに前のページの URL で「読み込みが終わった」を知らせるので、画面は、失敗の表示を持つタブの「終わった」の知らせでは、タブの URL を書き換えない。
  - **ログには書かない**：失敗した URL とエラーの説明の文は、画面に出すだけ（クエリに載るトークンなどが、ディスクに残るログに出ないように）。通しているタブの原因調べのログ（#409）は、種類と番号だけで、今までどおり。
- **子の webview**：タブごとに 1 つ、初めて出すときに作る（`app/src-tauri/src/browser.rs`。Tauri の `unstable` の `Window::add_child`）。グリッドは今のワークスペースの分しか描かないので、ほかのワークスペースに移る・グリッドに戻るときは隠すだけで、ページは残す。出す場所は画面（`app/src/ui/main-window/content/browser/BrowserArea.tsx`）が決め、毎フレーム見て、変わったときだけ殻に送る。
- **ページを置く座標**（#442）：画面は、ページを出す四角を viewport の左上からの論理ピクセルで測り、測ったときの viewport の大きさ（`innerWidth`×`innerHeight`）と一緒に殻に渡す（`browser_open`・`browser_bounds`）。Dialog のどこに置くかを決めるのは、殻の `app/src-tauri/src/browser_frame.rs` だけ。Linux は、wry の数え方（Dialog の中身の左上から）が画面の測り方と合うので、そのまま wry に渡す。macOS は、次の決まりで置く（#326 で、ページがタイトルバーの高さだけ上にずれた。直すたびに「どの view の、どの原点から数えるか」を足していたのを、1 つにまとめた）。
  - **数える座標は Dialog の座標**（原点は Dialog の左下、y は上向き）。画面の view（メインの webview）の枠も、ページの view の枠も、Dialog の座標に直してから比べる。view の親がどれか・親の高さ・親の向きには頼らない。wry の `set_position`・`set_size` は「親の view の高さ」から数えるので、macOS では使わない（作るときだけ wry が仮に置き、すぐに置き直す）。
  - **DOM の原点は、viewport の大きさから決める**。viewport は画面の view の左下に付いていて、view の方が大きい分は上と右の余白と見る（WebKit が中身を下げるのは上からだけ。view がタイトルバーの下に入った分など）。大きさが同じ（4 ピクセル未満の違い。画面は、表示の大きさを掛けて丸めた数を渡す）なら、viewport は view の枠そのもの。view の安全な領域（`safeAreaInsets`）は、決めるのには使わない：WebKit が、安全な領域の分だけ中身を下げるとは限らず、下げない場合に引くと、逆にページが下にずれるため。画面が自分で測った viewport の大きさなら、下げた場合も下げない場合も合う。
  - **Window の形が変わったら、殻が自分で追従する**。ページの四角は、viewport の 4 辺からの余白で覚える。画面の view の枠（と、その親の枠）が変わったという AppKit の知らせ（`NSViewFrameDidChangeNotification`）を受けたら、余白を保ったまま、その場で置き直す（リサイズ・フルスクリーンの出入り）。画面から同じ場所を送り直してもらうことも、待ち時間も要らない。画面が測り直した場所（サイドバーの幅など、DOM の中の変化を含む）は、今までどおり変わったときに届き、同じ決まりで置き直す。viewport の大きさだけが変わったときも、画面は送る（余白を決め直すため）。ただし、Dialog の端をドラッグしている間（画面の view の `inLiveResize`）に届いた場所では、余白を決め直さず、覚えている余白を使う（画面が測ってから殻に届くまでに view が大きくなった分を、余白と取り違えないように。ドラッグでは余白は変わらない）。
  - **ページの view を動かすのは殻のここだけ**。AppKit の自動リサイズは切る（wry は、親の大きさが変わると上の端に付いて動くようにしている）。
  - **確かめる手がかり**：端末から起動すると、標準エラーに `the page is placed in the screen` の行が出る（余白の決め方が変わったときだけ。画面の view の枠・viewport の大きさ・余白・安全な領域・画面が頼んだ四角）。置けなかったときは `the page was not placed` と理由が出る。
  - **macOS の実機で確かめる手順**：設定は `[gui.browser] enabled = true`。端末から起動して標準エラーをファイルに取り、内蔵ブラウザのタブで `https://example.org/` を出す。次のどの状態でも、URL バー（戻る・進む・読み込み直すと URL）が見え、ページが URL バーのすぐ下から Dialog の下の端まで、サイドバーの右の端から Dialog の右の端まで出ることを見る。
    1. フルスクリーンでない Dialog（起動したまま）。
    2. Dialog の右下の角をドラッグして大きさを変えている間と、変えたあと（ドラッグの間も、ページが URL バーの下に付いたまま動く。縦に大きくする間に、URL バーとページの間にすき間が出ないか・縦に小さくする間に、ページが URL バーに重ならないかを見る）。
    3. フルスクリーンにする・戻す（切り替わる動きの間は少しずれてもよい。終わったら合っている）。
    4. サイドバーの幅をドラッグで変える（ページの左の端が、サイドバーの右の端に付いて動く）。
    5. リーダー（Cmd+K）を出す・閉じる。ページ内検索（Cmd+F）を出す・閉じる（ページの大きさと位置が変わらない）。
    6. 表示の大きさ（画面全体の zoom）を変える。
    7. 外付けの画面があれば、Dialog をそちらへ移す。
    8. ほかのタブ・グリッドに切り替えてから Dialog の大きさを変え、ブラウザのタブに戻る（戻ったとき、合っている）。
    合わない状態があれば、その状態の名前と、標準エラーの `the page is placed in the screen`・`the page was not placed` の行を Issue に書く。
- **上に出るものとの重なり**：子の webview は画面（DOM）より上に重なる。ダイアログを出している間はページを隠す。ほかの重なるものは、自分に付けた印（属性）で避け方を決める（`app/src/ui/main-window/content/browser/overlay.ts` の `OVERLAY_SELECTORS`。物の種類ごとのクラス名では選ばない）。右下の Notice・リーダーの案内・右クリックのメニュー・ページ内検索の欄・トースト（浮かべるもの。`data-overlay`）は、macOS ではページを縮めず、画面（メインの webview。ページの場所の背景を透明にしてある）をページの webview より前に出して（同じ Dialog への `reparent`。`browser_layer`）ページの上に重ねる。ページはすりガラスのように見え（半透明の色をかぶせる。CSS の `backdrop-filter` は別の webview をぼかせない）、動画と音は止まらないが、マウスでもキーでも操作できない。Notice は閉じるまで残るので、閉じるまでページを操作できない（#439）。前に出すのは画面全体で、Notice の部分だけにはしていない（macOS の view の重なりは view 単位で、部分だけ前に出すには、画面の view のクリックの当たり判定を差し替える必要があるため）。重なりが消えたらページを前に戻す。Linux と Windows は、浮かべるものはページの下の端をそれの上まで上げて避ける（縦だけ縮める。横に縮めると、ページの組み直しで読んでいた所を見失うため。低くなりすぎるなら隠す）。
- **キー**：リーダーの `o` のグループ（`docs/key-design.md` の 3.2）。ブラウザを出している間は、Cmd+R / Ctrl+Shift+R がページを読み込み直す（ほかのときはリサイズモード）。ブラウザの操作は場所のキーにしない。ページの中のキー（GitHub の `t`・`?` など）は、ページに渡す。
- **ページにキーがあるときのリーダー**：ページにキーがあると、画面の `window` の `keydown` には届かない。そこで、ページに入れるスクリプト（`browser_keys.js`。どのフレームにも入れる。ページの外の世界で動かす。下の「ページに Tauri の命令を使わせない」）が、リーダーと Shortcut に当たるキーだけを止めて、`kisui-key:` の URL を `window.open` で開こうとする。殻の `on_new_window` がそれを受けて開かずに断り、登録してあるキー（リーダーと Shortcut）か、リーダーの続きのキーなら、キーを画面に知らせてから、キーをメインの webview に移す。リーダーのあとは、キーが移るまでの短い間（1.5 秒か、ページからキーが外れるまで）のキーも同じように渡す（速く打った続きのキーがページに届かないように）。操作が終わり（リーダーなら出て）、画面のキーの行き先がそのままなら、キーをページに戻す。遷移（URL の書き換え）ではなく `window.open` にしたのは、ページの `beforeunload` を起こさないため。Tauri のアプリのメニューのアクセラレータで受ける形は、Linux にメニューバーが無く、使わなかった。
- **macOS の矢印キーの豆腐**：macOS の子の webview（`add_child`）は、カーソルが動けない方向に矢印キーを押すと、矢印キーに使う私用領域の文字（U+F700〜）をテキストとして入力してしまう（tauri-apps/tauri#10194。空の入力欄では毎回）。殻には手を入れず、同じ `browser_keys.js` が `beforeinput`（`insertText`）で U+F700〜U+F74F（AppKit の関数キーの文字の区画。U+F8FF の Apple のロゴは打てるよう止めない）を含む入力だけを止める。`keydown` は止めないので、カーソルの移動もページの矢印キーの処理も変わらない。
- **ページに Tauri の命令を使わせない**：子の webview は外の URL（`WebviewUrl::External`）で、tauri は `remote` を持つ capability の無い外の URL からの IPC を断る。capability はメインの webview にだけ与える（`capabilities/default.json` は `webviews: ["main"]`。`windows: ["main"]` にすると、同じ Dialog に置く子の webview にも当たる）。殻の命令は、呼んだ webview が `main` かも確かめる（`from_main`）。キーを知らせる URL には、webview を作るたびに決める nonce を入れ、合わないものは捨てる。nonce を持つスクリプト（`browser_keys.js`・`browser_passkey_tell.js`・`browser_close_tell.js`）は、ページの外の世界（isolated world。Linux は WebKitGTK の world、macOS は `WKContentWorld`）で動かす。ページのスクリプトは、その世界の変数も関数も見られず、差し替えられないので、nonce を読めず、キーを真似できない（`isTrusted` でないキーも渡さない）。ページの世界では動かさない：WebKit は、ページのスクリプトが組み込みの関数を差し替えた後の同じ世界で、差し込んだスクリプトをもう一度動かすことがあり、そこでは先に取っておいた関数も信用できない。wry の `initialization_script` はページの世界にしか入れられないので、webview を作った直後（同じメインスレッドの処理の中）に、OS の WebView に直接足す（`browser.rs` の `add_world_scripts`。足せなければ、nonce をページの世界に置かず、そのタブではページにキーがある間のリーダーと Shortcut を効かせない。macOS 10.15 以前は `WKContentWorld` が無く、足せない）。ページが呼ぶ関数を差し替えるスクリプト（`browser_passkey.js`・`browser_close.js`）はページの世界で動かすしかないので、nonce を持たせず、自分のフレームの `window` にイベントを送らせ、外の世界のスクリプトがそれを受けて殻に知らせる（ページが同じイベントを送っても、起きるのは、ページがその関数を呼んだときと同じこと）。殻は、nonce が合っても、タブを作るときに登録したキー（リーダーと Shortcut）と、リーダーに入るキーのあと 2 秒の間の続きのキーのほかは、画面に渡さない（`accept_key`）。nonce を知られても、できるのはリーダーと Shortcut を押すことまで（リーダーの木の操作は動かせる。Dialog の中の操作とターミナルへの入力は、画面の本物のキーでしか動かないので、できない）。
- **遷移と新しい Window**：子の webview の遷移は http・https・about だけ許す。新しい Window（`target=_blank`・`window.open`）は、下の「シークレットのタブ・新しい Window・ダウンロード（#204）」。
- **ログインとタブを残す**：ログイン（Cookie などのページのデータ）は、すべてのタブで 1 つを共有し、ディスクに残す。Linux はデータのフォルダ（`~/.local/share/dev.mm1995tk.kisui-terminal`）の `browser/`、macOS は WKWebView の既定の置き場（`~/Library/WebKit/dev.mm1995tk.kisui-terminal` など。場所は OS が決める）。開いていたタブ（開いたときのターミナルのタブと URL と題）は、データのフォルダの `browser-tabs.json`（自分だけが読めるファイル）に覚え、再起動したら戻す（どのワークスペースもターミナルのタブから始め、ページはタブを出したときに読み込む）。どのワークスペースのタブか、タブの名前は、GUI のワークスペースの記録（webview の localStorage）が持つ。設定のフォルダには書かない。


## シークレットのタブ・新しい Window・ダウンロード（#204）

- **シークレットのタブ**：リーダーの `n` で開く Workspace switcher の、作るタブの種類の `B`（#456 までは `o N`）。タブごとに別の、ディスクに残さないデータを使う（tauri の `incognito`。Linux は WebKitGTK の ephemeral な WebContext、macOS は WKWebsiteDataStore の nonPersistent）。共有のログインも、ほかのシークレットのタブのログインも見えない。閉じるとログインは消え、`browser-tabs.json` にも書かない（再起動しても戻さない）。サイドバーの行に「シークレット」の札を付ける。パスキーを外のブラウザに移す仕組み（#206）は使わない（パスキーのスクリプトを入れない）。写した Cookie は外のブラウザに残り、「残さない」と食い違うため。パスワードと認証アプリのコードでのログインはできる。
- **新しい Window**：ページが開く新しい Window（`target=_blank` のリンク・`window.open`）は、開いた元のタブと同じワークスペースの新しいタブにして出す。開いた元のページとの連絡（`window.opener`）を保つため、WebKit が求める形で webview を作り、`on_new_window` から `NewWindowResponse::Create` で返す（Linux は元の webview に関係付けた webview（related view。データも元と同じ）、macOS は WebKit が渡した設定で作った webview）。tauri の `Create` は「Window の最初の webview」しか受けないので、隠した Dialog に子の webview として作って返し、返したあとメイン Window に移して（`Webview::reparent`）、隠した Dialog を壊す。そのあと画面に知らせ（`browser-popup`）、画面はタブを足す（webview はもうあるので作らない）。データは開いた元と同じなので、シークレットのタブから開いたタブはシークレット（覚えない）。開いたタブは、ふつうのタブと同じく覚える（再起動したら、開いた元との連絡の無いふつうのタブとして戻る）。新しいタブを作れなければ、今まで通り同じタブで開く。ページが `window.open` を繰り返してもタブを増やし続けないよう、1 つのタブ（と、そこから開いた新しいタブすべて）が新しい Window を開けるのは、合わせて 10 秒の間に 5 つまでにし、超えた分は断る（macOS の WKWebView は、ユーザーの操作の無い `window.open` も既定で通すため。Linux の WebKitGTK は既定で止める）。macOS では、WebKit が渡す設定がスクリプトの入れ物（`WKUserContentController`）を開いた元と共有するので、新しいタブにはスクリプトを足さず、開いた元のタブと同じ nonce で知らせを受ける。
- **ページが自分を閉じる**：`window.close()` で、タブを閉じ、開いた元のタブ（同じワークスペースにあれば）に戻る。Linux は WebKitGTK の `close` を直接受ける（wry は webview を壊すだけで殻に知らせないため。`webkit2gtk` を直接使う）。macOS は wry が `webViewDidClose` を受けないので、ページに入れるスクリプト（`browser_close.js`。上のフレームだけ。ページの世界）が `window.close` を差し替え、ページの外の世界のスクリプト（`browser_close_tell.js`）が、キーと同じ形（`kisui-close:` の URL と nonce）で殻に知らせる。閉じてよいのは、ふつうのブラウザと同じく、ほかのページが開いた Dialog か、履歴が 1 つだけのページ。
- **ダウンロード**：OS のダウンロードのフォルダ（tauri の `download_dir`。ふつうは `~/Downloads`）に、場所を聞かずに保存する（`app/src-tauri/src/download.rs`）。名前はページが勧めたものの最後の部分（フォルダの区切りと制御文字を除く）で、同じ名前があれば `名前 (1).拡張子` `名前 (2).拡張子` … と番号を付ける（wry と同じ付け方）。終わったら右下の Notice で知らせ（`browser-download`）、「開く」（OS の既定のアプリ）と「フォルダを表示」（macOS は Finder でファイルを選んだ状態、Linux はフォルダを開く）ができる。キーはリーダーの `i o` `i f`（いちばん新しいダウンロード）。開く・表示するのは殻が保存したファイルだけ（画面は番号で頼み、パスは渡さない）。Linux のダウンロードは WebContext（データの単位）に届くので、WebContext ごとに 1 度だけ受け口を足す（wry の受け口は webview ごとに足すので、共有のデータを使うタブの数だけ重なり、最初のタブを閉じると断るようになる）。macOS は webview ごとに受ける（tauri の `on_download`。終わったときにパスが来ないので、始めたときに覚える）。
## URL を内蔵ブラウザのタブで開く（#203）

内蔵ブラウザを有効にした人が、ターミナルに出た URL や `kisui open` の URL を、作業中のワークスペースのタブで開けるようにした。無効なら、今まで通り外部ブラウザで開く。

- **入口**：`kisui open <URL>` と shj の URL を開く要求（どちらも通知 `browser.open` `{workspaceId, url}`）は、そのワークスペースの新しいタブで開く。ターミナルの URL の `cmd + click`・`cmd + shift + click`（macOS 以外は ctrl）は、今のワークスペースの新しいタブで開く（`app/src/features/browser/pages.ts` の `openUrlFor`・`openInNewTab`）。開いたタブを出し、今のワークスペースならページにキーを向ける。ほかのワークスペースの通知なら、そこへは移らない（`pane.show` と同じ。そのワークスペースに移ると、タブのページが出ている）。取り決め（`kind: "browser"`）そのものは変えていない。
- **外部ブラウザで開くクリック**：`cmd + option + click`（macOS 以外は `ctrl + alt + click`）。`shift` を足しても同じ（マウスの報告を有効にしたアプリが動いている間は、`shift` 付きのクリックだけが GUI に届くため）。`cmd + shift + click` は「マウスを使うアプリが動いていても開く」意味のまま残した。開いたページを外部ブラウザに移すのは、ブラウザのタブの Dialog（リーダーの `a`）の `e`（#459 までは `o e`）。
- **キーでは開かない**：画面の URL をキーで選んで開く操作は作らない。
- **リモートのマシンの `localhost`**：外部ブラウザと同じ `kisui relay` の中継（上の「GUI の外部ブラウザ」・relay.md）を通す。殻の命令 `browser_resolve_url`（`open_url.rs`）が中継を用意して、タブに開かせる手元の URL（`http://127.0.0.1:<手元のポート>/…`）を返す。誰も待っていなければ、タブを作らずに理由を出す（外部ブラウザと同じ）。タブが覚えて入力欄に出すのは中継前の元の URL で、ページの遷移で殻から届く中継の URL は、同じ origin なら元の origin に戻してから書く（`app/src/features/browser/relay.ts`）。戻る・進むで前の中継の URL に戻ることもあるので、対応はタブごとにこれまで使ったものを全部覚え、タブを閉じたときに捨てる。再起動して戻したタブも、出すときに改めて中継を用意する。ページの中の絶対 URL の `http://localhost:…` が中継を通らないのは、外部ブラウザと同じ（今は対処しない）。
- **待ち受けのポート**：起動し直しても同じ番号になりやすくした（上の「リモートのマシンの `localhost`」）。ページの origin（`127.0.0.1:<ポート>`）が起動のたびに変わると、localStorage などが起動のたびに別になるため。

## 内蔵ブラウザのプロキシ（macOS。#294）

macOS の内蔵ブラウザ（WKWebView）は、IPv6 の無い回線で Cloudflare WARP を使うと、Google に IPv4 の出口でつながり、`www.google.com.hk` に移される（#287）。macOS の名前解決が IPv6 のアドレスを返さないため。そこで、内蔵ブラウザを有効にしていれば、全部のタブを手元で動かす中継型（relay）のプロキシ `masque-proxy`（workspace の独立した crate。#290・#292）に通す。プロキシは行き先の名前を自分で DNS に問い合わせ、IPv6 に先につなぐ。TCP は Happy Eyeballs（RFC 8305）でつなぐ：IPv6 と IPv4 のアドレスを IPv6 から交互に試し、前の試みが 250 ミリ秒のうちにつながらなければ次も試し始めて、先につながった方を使う。IPv6 のアドレスはあっても行き先まで届かない回線でも、IPv6 のアドレスの数だけ待たずに IPv4 でつながる。行き先の名前ごとに、TCP で IPv6 も試したのに IPv4 が先につながったことを 10 分だけ覚え、その行き先には、UDP（CONNECT-UDP。HTTP/3）は IPv4 を先にし、TCP も IPv4 から試す。UDP には接続の確立が無く、経路さえあれば IPv6 への送り先を決められてしまうので、覚えておかないと、その回線では HTTP/3 の packet が全部消える。IPv4 から試した接続では覚え直さず（覚えた時刻を延ばさない）、切れたら IPv6 から試し直す。TCP で IPv6 が先につながったら忘れる。中継型なので HTTP/3 も運び、全部のサイトを通しても HTTP/3 が残る（Google のドメインだけにしない）。Linux（WebKitGTK）は何も変えない（`app/src-tauri/src/browser_proxy.rs`）。

- **動かし方**：プロキシは殻のプロセスの tokio のランタイム（tauri の非同期のランタイム）で動かす。子のプロセスにしないのは、鍵をプロセスの外に渡さずに済み、殻と一緒に終わるため。待ち受けは `127.0.0.1` だけで、HTTP/3（UDP）と HTTP/2（TCP）のポートは起動のたびに空いているものを取る。
- **WKWebView への設定**：データストアの `proxyConfigurations`（macOS 14 から）に、Network.framework の中継の設定（`nw_relay_hop_create` に `localhost` の HTTP/3 と HTTP/2 の口を渡し、`nw_proxy_config_create_relay` にしたもの）を入れる。Tauri の `proxy_url` は `http://` と `socks5://` しか受けないので使わない。データストアは 3 種類あり、どれも通す。
  - 共有のもの（`defaultDataStore`）：プロキシを用意したときに 1 度入れる。
  - シークレットのタブのもの：タブごとにディスクに残さないデータストアを作ってプロキシを入れ、それを持つ WebView の設定でタブを作る（`with_webview_configuration`。tauri の `incognito` では、作ったあとでないとデータストアに触れず、最初の読み込みに間に合わない）。
  - 新しい Window のタブ（`Data::Opener`）：WebKit が渡す設定は開いた元のタブのデータストアを持つので、元と同じく通る。
  - プロキシにつながらないとき（止まった・信頼が外れた）は、プロキシ無しでつなぐ（`nw_proxy_config_set_failover_allowed`）。ブラウザは使えるが、IPv4 の出口になる。
  - `localhost`・`127.0.0.1`・`::1` はプロキシに通さない（`nw_proxy_config_add_excluded_domain`）。リモートのマシンの `localhost` を中継で開くタブ（`http://127.0.0.1:<手元のポート>/…`。上の「URL を内蔵ブラウザのタブで開く（#203）」）に回り道をさせない。通ってしまっても、プロキシは `127.0.0.1` につなぐ（IP のリテラルは問い合わせない。`localhost` は DNS のライブラリが loopback に引く）。
  - macOS 13 以前（`nw_relay_hop_create` が無い）は、何も聞かずにプロキシ無しで動く。この関数は、古い macOS でも起動できるよう、リンクせずに `dlsym` で探す。
- **証明書の信頼**：WKWebView は、中継のプロキシの TLS で、OS に信頼された証明書しか通さない（`relay_tls_options` の検証の block が効かない。#290）。そこで次の形で信頼させる。
  - Mac ごとに、その Mac だけの鍵と自己署名の証明書を作る（`masque_proxy::Identity::generate`）。全員に同じ鍵を配らない。証明書は `localhost`・`127.0.0.1`・`::1` 用で、CA ではなく（`basicConstraints` が CA でない）、用途は TLS のサーバーだけ。名前（CN）は `kisui-terminal browser proxy (localhost)`。
  - 証明書をログインのキーチェーンに入れ、用途を SSL、名前を `localhost` に限って信頼させる（`SecTrustSettingsSetTrustSettings` を利用者の領域で。`security add-trusted-cert -r trustRoot -p ssl -s localhost` と同じ）。macOS がパスワードを聞く。中継の行き先の名前を `localhost` にするのは、TLS で確かめる名前を信頼の名前に合わせるため。
  - 鍵（と証明書）は、ファイルに置かず、ログインのキーチェーンの項目（generic password。service が `kisui-terminal browser proxy`）に置く。項目を読めるのは、作った kisui-terminal だけ（キーチェーンの既定の決まり）。kisui-terminal は Apple の署名が無い（ad-hoc 署名）ので、版を上げると別のアプリと見なされ、macOS が項目を読んでよいかを聞く（「常に許可」で、その版では聞かなくなる）。断られたら、その起動ではプロキシを使わない。
  - 聞くのは、内蔵ブラウザで初めてタブを開くとき（内蔵ブラウザを使わない人には聞かない）。答えを待つ間、そのタブ（と、同時に開くほかのタブ）は作らずに待つ。すでに信頼されていれば聞かない（`SecTrustEvaluateWithError` で、名前 `localhost` の SSL として確かめる）。
  - 断られたら、プロキシを使わず、今までどおり開く。断られたことはデータのフォルダの `browser-proxy-declined` に覚え、次の起動からは聞かない（作らない・作り直さない。パスワードを聞く画面を、起動のたびに出さないため）。消すと、次の起動で聞き直す。初めての信頼を断られたら、作った証明書と鍵の項目を消す（断った人のキーチェーンに残さない。残すと、版を上げたあとに項目を読んでよいかを聞かれる）。断られたのでなく失敗したとき（キーチェーンに書けないなど）は覚えず、次の起動で試し直す。
  - どの身元を使うか・聞くかは、キーチェーンに触れない関数（`plan`。入力は、断ったか・覚えている証明書の切れる時刻・信頼されているか・今の時刻）で決め、テストで確かめる。
  - 証明書の有効な長さは 365 日（macOS は TLS のサーバーの証明書で 825 日を超えるものを信頼しない）。切れるまでが 30 日を切ったら、初めてのタブを開くときに作り直し、新しい証明書の信頼を聞く。信頼させられたら、キーチェーンの項目を差し替え、古い証明書とその信頼を消す（`security delete-certificate -t`。ここでも macOS がパスワードを聞く）。新しい方を信頼させられなければ、新しい証明書を消し、まだ切れていない古い方を使う。断られたときは、次の起動からも聞かずに、信頼されたまま切れていない古い方を切れるまで使う（切れたら、プロキシを使わない）。
  - 信頼を外す操作はアプリに無い。README に、信頼を外して証明書と鍵を消す `security` のコマンドを書いた。
- **DNS のサーバー**：OS に設定されたもの（macOS は System Configuration の `State:/Network/Global/DNS`。WARP なら `127.0.2.2`）を、問い合わせる前に 5 秒に 1 度まで読み直し、変わっていたら新しいサーバーに問い合わせる（`masque-proxy` の `Dns::System`）。起動のときに 1 度読むだけだと、Wi-Fi を移る・WARP を入れ切りするなどでサーバーが変わったあと、名前を引けなくなるため。起動のときに設定が無くても（回線につながっていない）プロキシは起動し、設定が出てから問い合わせる。

## 通信を記録するプロキシ（#409）

Burp や Caido のように、通信を見て書き換えられるようにする機能の 1 つ目（決めたことは #209）。内蔵ブラウザのタブとターミナルのタブの HTTP・HTTPS の通信を、kisui のプロキシに通して、一覧と中身を見る。書き換えて送り直す（#410）は下の「書き換えて送り直す（#410）」、途中で止めて書き換える（#411）は「途中で止めて書き換える（#411）」。上の「内蔵ブラウザのプロキシ（macOS。#294）」とは別のもの（あちらは中身を見ない中継で、全部のタブを通す）。

- **本体は kisui（Go の `proxy` パッケージ）**：`kisui serve` が、通すと決めたタブごとに 1 つ動かす（取り決めは `docs/design/gui-protocol.md` の「プロキシ」）。ターミナルのタブは、そのタブのマシンの `kisui serve`（ssh 先のマシンなら、そのマシンで動く）、ブラウザのタブは、手元のマシンの `kisui serve`。`kisui proxy` は、同じものを Dialog と関係なく単独で動かす。依存は足さず、Go の標準ライブラリだけで作った（`net/http`・`net/http/httputil` の `ReverseProxy`・`crypto/tls`・`crypto/x509`）。
- **通すのは選んだタブだけ**：既定は通さない。待ち受け口はタブごとに別のポートにし、どのタブの通信かは、どのポートに来たかで分ける（プロキシの認証で分ける案は、WebView がプロキシの認証を受けるかが OS ごとに違うので採らなかった）。待ち受けは `127.0.0.1` だけ。認証は付けていないので、同じマシンのほかのユーザーも、そのポートをプロキシとして使える（使った通信は記録に出る。認証局の秘密鍵は読めない）。
- **証明書**：kisui がマシンごとに自前の認証局を 1 つ作り、状態を置くフォルダに置く（秘密鍵は 0600）。OS には入れない。通したタブだけが信じる。行き先の証明書は、プロキシが OS の認証局で確かめ、正しくなければ 502 を返す（行き先につながらなかった理由のヘッダー付き。内蔵ブラウザのタブは、それを見て「開けなかった」画面を出す。上の「GUI の内蔵ブラウザ」の「読み込みの失敗の表示」）。
- **ターミナルのタブ**：パネルを開いたあとに開いたペインに、`HTTPS_PROXY`・`HTTP_PROXY` と、認証局を信じさせる変数を渡す（動いているシェルの環境変数は変えられない）。認証局の変数のうち、OS の束を丸ごと置き換えるもの（`SSL_CERT_FILE` など）には、OS の束に認証局を足したファイルを渡す。認証局だけのファイルを渡すと、その変数は読むがプロキシの変数は読まないプログラムが、行き先に直接つないで、OS の認証局の証明書を確かめられなくなるため。
  - プロキシの変数は読むが、認証局の変数は読まないプログラムは、通らないのではなく、証明書のエラーで通信できなくなる。例：macOS の Go 製のプログラム（`gh`・`terraform` など。macOS の Go は証明書をキーチェーンで確かめ、`SSL_CERT_FILE` を見ない）、Java のプログラム（自前の認証局の置き場を使う）。戻すには、通すのをやめて（`x s`）、新しいペインを開く。認証局を OS に入れないと決めたので、こういうプログラムは通せない。
  - 通すのをやめても、待ち受け口は閉じず、中身を見ず・記録もせずに中継だけを続ける。変数を持ったままのペインのプログラムが、通信できなくならないように。閉じるのは、タブ（ワークスペース）を閉じたとき。
  - `kisui serve` の引き継ぎ（版を上げたとき）では、待ち受け口を fd ごと次の serve に渡す。同じ理由。
- **ブラウザのタブ**（`app/src-tauri/src/browser_capture.rs`）：パネルを開くと、そのタブの webview を、プロキシ付きで作り直す（ページを読み直す）。
  - **そのタブだけの、ディスクに残さないデータを使う**（シークレットのタブと同じ形）。OS の WebView は、プロキシをタブ（webview）ごとではなく、ページのデータ（Cookie などの置き場。macOS は WKWebsiteDataStore、Linux は WebsiteDataManager）ごとに決める。Tauri の `proxy_url` も、その webview のデータに設定する。共有のデータ（ふつうのタブ全部が使う）に設定すると、ほかのタブも通ってしまい、「通していないタブの通信は、プロキシを通らない」を満たせない。そこで、通すタブはデータを分ける。代わりに、通している間は共有のログインが見えない（通したタブの中でログインし直す。その通信も記録に出る）。共有の Cookie を通すタブに写す案は、この Issue ではやらない。
  - ページが開いた新しい Window のタブは、開いた元のタブと同じデータを使うので、同じプロキシに通り、同じ一覧に出る。
  - **WebView には、証明書を確かめさせない**：OS の WebView には、認証局をデータごとに足す口が無い（OS 全体に入れるしかないが、入れないと決めた）。そこで、通すタブのデータに限って、WebView に証明書を確かめさせない。Linux（WebKitGTK）は、そのデータの TLS のエラーを無視する設定（`TLSErrorsPolicy::Ignore`）。macOS（WKWebView）は、証明書の確認の問い合わせ（`webView:didReceiveAuthenticationChallenge:completionHandler:`）に、通しているタブの webview のときだけ「この証明書を使う」と答える。このタブの通信はすべて `127.0.0.1` のプロキシに行き、行き先の証明書はプロキシが確かめるので、確かめる役が WebView からプロキシに移るだけで、確かめない通信は無い。ほかのタブとメインの画面は変えない。
    - **macOS の App Transport Security（ATS）の例外**：ATS が掛かっている間は、問い合わせに「使う」と答えても信頼の確認を緩められず、WebKit の通信の TLS が `errSSLATSViolation`（`-9880`）で失敗する（読み込みは `-1200`、プロキシには `bad certificate` の alert が届き、ページは白いまま。#409 の開け直しの原因）。そこで、`app/src-tauri/Info.plist` に `NSAppTransportSecurity` の `NSAllowsArbitraryLoadsInWebContent` を書き、WebView（WKWebView）の通信に限って ATS を外す（`tauri build` が、生成する Info.plist に重ねる。配る版のビルド（`build.yml`）は、できた .app に鍵が入ったかを確かめる）。Nix のパッケージ（`packaging/nix/kisui-terminal.nix`）で入れた macOS 版には効かない：`.app` を作らず、`cargo build` した実行ファイルをそのまま置き、tauri-codegen が Info.plist を実行ファイルに埋め込むのは `tauri dev` のときだけなので、ATS の既定が掛かったままで、通したタブのページは出ない。
      - 範囲を WebView に限る鍵なので、ATS を外す鍵の中でいちばん狭い。WebView の外の、ATS の掛かる通信（URLSession など）には ATS が残る。この鍵があると `NSAllowsArbitraryLoads` は無視されるので、書かない。ドメインごとの例外（`NSExceptionDomains`）は、通すタブが任意のサイトを開くので使えない。
      - 外れるのは、ATS の上乗せの確認（TLS 1.2 以上・前方秘匿・鍵と署名の強さ）と、外の `http://` を止める動き。全部の WebView（メインの画面・通していないタブ・シークレットのタブ）に効くので、内蔵ブラウザで外の `http://` のページが開けるようになる。通していないタブの証明書の確認（OS の認証局で確かめる既定の扱い）は変わらない。
      - 認証局を OS に入れる方針の変更ではない（入れないまま）。
    - 証明書を 1 つずつ確かめて許す方法（Linux の `load-failed-with-tls-errors` で、そのホストの証明書を許す）は採らなかった。その知らせはページ本体の読み込みにしか来ず、ページが読むほかのホスト（CDN など）が通らないため。
    - macOS の問い合わせの受け口は、wry が webview に付ける WKNavigationDelegate のクラスに、実行時に足す（`class_addMethod`）。wry はこの受け口を持たず、外から足す口も無いため。WebKit は delegate を付けたときに受け口の有無を覚えるので、足す前に作った webview（メインの画面・ほかのタブ）は、今までどおりの扱いのまま。wry がこの受け口を持つようになったら、足さずに、通せないと答える（上書きしない）。
    - macOS で通したタブのページが出ないことがあり（#409 の開け直し。読み込みが TLS のエラー `-1200` で失敗し、プロキシの一覧に何も出ない）、原因を見分けるため、次をログに書く。macOS の Dialog は、統合ログ（`NSLog`。`log stream --predicate 'process == "kisui-terminal"'` で見える。行の頭は `kisui-terminal: proxied tab:`）に、通すデータストアを作ったこと、証明書の確認の問い合わせが来たことと答え（「使う」と答えたことは、見たサイトの名前が溜まらないよう、データストアごとに最初の 1 回だけ）、通しているタブの読み込みの失敗（`webView:didFailProvisionalNavigation:withError:` を同じく delegate のクラスに足す。書くのはエラーの種類と番号だけ：エラーと下の層のエラーの domain と code、TLS のエラーの番号、行き先のホストの名前、行き先の証明書が届いていたか。エラーの説明の文は書かない（失敗した URL の全体が入り、クエリのトークンなどがログに残るため））を書く。通しているタブが無い間は書かず、ほかのタブの問い合わせは行き先の名前を書かない。`kisui serve` のプロキシは、`serve.log` に、プロキシごとに最初の CONNECT と、CONNECT を断ったこと・クライアントとの TLS の handshake が切れたこと（理由つき）を書く。うまくいった通信は書かない（記録は一覧にある）。
    - この作りが安全なのは、`127.0.0.1` のそのポートで待ち受けているのが kisui のプロキシである間だけ。手元の `kisui serve` との接続が切れたら（落ちた・止められた）、Dialog は、つなぎ直しを待たずに、通しているブラウザのタブをプロキシ無しに戻す（空いたポートで、同じマシンの別のプロセスが待ち受けて、証明書の警告なしで通信を読めないように）。`kisui serve` の引き継ぎでも接続は 1 度切れるので、そのときも戻る（ターミナルのタブは通したまま）。
      - 戻すとき、webview はすぐに作り直す（出していないタブも。作ったあと隠す）。画面の毎フレームの見回り（`requestAnimationFrame`）に任せると、作り直すのは出しているタブだけで、Dialog が隠れている間は WebView が見回りを止めるので、止まったポートをプロキシにした webview が、タブを出すまで・Dialog が見えるまで残る（#409 の macOS の確認で、`kisui serve` を止めてもタブが読み直されなかった原因）。
      - macOS では、通さずに作り直すタブを元にしたデータストアを、通しているタブのものとして覚えるのをやめる。閉じたときに忘れるのは、そこから開いた新しい Window のタブまで全部閉じたときだけなので、それだけだと、新しい Window のタブが残っている間、通しているタブがあることになったまま残り、ほかのタブの証明書の確認がログに出続けた。
  - macOS は 14 以降（データごとのプロキシの設定 `proxyConfigurations` が要る）。13 以前は、通せないと答える。
  - **#294 の中継型のプロキシとの関係**：通すタブは、#294 のプロキシには通さない（プロキシを 2 つ重ねない）。通している間、そのタブは、kisui のプロキシが OS の名前解決で行き先につなぐ。IPv6 の無い回線で Cloudflare WARP を使っていると、#287 の現象（Google が別の国のサイトに移す）が、通しているタブでは出る。kisui のプロキシの先に #294 のプロキシをつなぐ案は、Go から HTTP/2 の CONNECT とキーチェーンの証明書を扱うことになり、通すタブでその現象が困るかが分かってから決める。
- **パネル**（`app/src/features/proxy/`・`app/src/ui/main-window/content/proxy/`）：リーダーの `x p` で開く。グリッドの場所を左右に分け、右に一覧と中身を出す（幅は場所の 45%）。パネルを閉じても、タブは通したまま記録を続ける。やめるのは `x s`。開いているかは、タブごとに覚える。通しているかは `kisui serve` が持つので、Dialog を開き直しても、ターミナルのタブは通したまま戻る（ブラウザのタブは、通していないタブに戻る）。
- **本文の圧縮**：記録している間は、行き先に `gzip` だけを頼む。ブラウザは `br`・`zstd` を頼むが、Go の標準ライブラリでは展開できず、本文を見せられないため。応答は書き換えずにクライアントに返す。

## 書き換えて送り直す（#410）

プロキシのパネルで選んだ通信の要求（メソッド・URL・ヘッダー・本文）を書き換えて、もう一度送る。取り決めは `docs/design/gui-protocol.md` の `proxy.resend`。

- **送るのはプロキシ（`kisui serve`）**：Dialog は書き換えた要求を `proxy.resend` で渡すだけで、送るのは、その通信を記録した scope のプロキシ（ターミナルのタブなら、そのタブのマシンの `kisui serve`）。行き先へは、クライアントの通信と同じく直接つなぎ、行き先の証明書を OS の認証局で確かめる。応答は、ページやシェルには返さず、同じ記録に新しい通信（`resentFrom` に元の通信の id）として入れる。Dialog は、送った通信を選び、応答の側を出す。
- **画面の形**：パネルの下の部分（選んだ通信の中身）を、書き換える欄に置き換える（パネルの `e`）。別の Dialog（ダイアログ）にしなかったのは、送ったあとの応答が同じパネルの一覧と中身に出るので、行き来をパネルの中で済ませるため。欄は、メソッドと URL の 1 行、ヘッダー（1 行に 1 つ、`名前: 値`）、本文。送るのは Cmd+Enter・Ctrl+Enter（DB のタブの SQL の実行と同じ字）、やめるのは `Esc`。書き換えている間は、一覧の行を押しても選び直さない（書いたものを失わないよう）。書き換えたものは送るかやめると捨てる（覚えておかない）。
- **下書きの作り方**（`features/proxy/model.ts` の `draftFrom`）：URL は記録した scheme・host・path から作る。`Host` は URL のホストと同じなら欄に出さない（URL から決まる。違えば残す：プロキシに絶対 URL で送った要求の `Host` が URL と違うとき）。`curl --connect-to` のように、`CONNECT` で頼まれた行き先と中の要求の `Host` が違った通信は、URL は `Host` の名前のまま、記録したつないだ先（`proxy.detail` の `connectTo`）を「つなぐ先」の欄に出し、`proxy.resend` の `connectTo` で同じ所に送る（そうしないと、手元の開発用のサーバーに向けて試していた要求が、`Host` の名前の本物のサーバーに届く）。欄を空にすると、URL のホストに送る。`Content-Length`・`Transfer-Encoding` は出さない（本文から決まる）。
- **本文**：記録は本文を先頭の 256 KiB までしか覚えないので、字の本文だけを欄で書き換える。字でない本文と、圧縮した本文（要求に `Content-Encoding` がある。記録は展開して見せるので、展開した字を送ると `Content-Encoding` と合わなくなる）は、欄を出さず、`kisui serve` が覚えたままのバイトを送る（`body` を省く）。上限で切れた本文は、元のままでは送れないので、空の欄から書いたものを送る（`kisui serve` も、`body` を省いた切れた本文は断る）。字でない本文を書き換える口（ファイルから読むなど）は入れていない。
- **`Accept-Encoding`**：記録している間と同じく、行き先には `gzip` か `identity` だけを頼む（ブラウザの通信を書き換えずに送り直すと `br` を頼み、応答の本文を見せられないため）。記録には書いたままのヘッダーを残す。`User-Agent` を書かなければ付けない（Go の既定の `Go-http-client` を足さない）。
- **同時に送り直す数**：1 つのプロキシで 16 まで。終わらない応答（SSE など）を何度も送り直して、受ける処理が溜まり続けないように。待ち受け口を閉じる（`x s`・タブを閉じる）と、受けている途中の応答も切る。
- **古い `kisui serve`**：`capabilities` の `"proxy.resend"` で見分け、無ければ `e` で「古い版」と知らせる。
- **信頼の範囲**：`proxy.resend` は、Dialog とつながった（`session.hello` を済ませた）接続からだけ受ける。`kisui serve` は Dialog の頼みでシェルも動かせるので、任意の URL に要求を送れることで、できることは増えない。プロキシ自身の待ち受け口を指す要求は断る（自分に戻る輪を作らない）。

## 途中で止めて書き換える（#411）

プロキシに通したタブの要求を、行き先に送る前に止め、パネルで、そのまま流す・書き換えて流す・捨てる、を決める。Burp や Caido のような機能の 3 つ目。取り決めは `docs/design/gui-protocol.md` の `proxy.hold`・`proxy.release`、実装は Go の `proxy/hold.go`。

- **止める・止めないは、タブ（scope）ごと。既定は止めない**：切り替えは、パネルの `i`（頭のボタンでも）と、リーダーの `x i`。リーダーにも載せたのは、止めている間はそのタブのページやコマンドが待つので、キーがターミナルやページにあるままでも、すぐにやめられるように。
- **止める場所**：プロキシが要求を受けて、行き先に送る直前（`Proxy.forward`）。要求は、記録に `state` が `held` の通信として足し、`proxy.release` が来るまで、その要求を受けた処理が待つ。流すと、同じ通信（同じ `id`）のまま進む。
- **止めるのは要求だけ**：応答は止めない。応答も書き換えられるようにするには、応答を書き換える欄と、圧縮した本文を展開して書き換えたあと圧縮し直す仕組みが要る。完了条件（止めた要求を書き換えて流す）の外なので、この変更には入れていない。止める通信の絞り込み（ホストなど）も入れていない（切り替えはタブごとだけ）。パネルから送り直す要求（`proxy.resend`）は止めない（自分で書いて送ったものなので）。
- **本文**：大きさが分かっていて（`Content-Length`）記録の上限（256 KiB）までなら、止める前に読んで記録に入れる。止めている間に中身を見て、書き換えられる。大きさが分からない本文（chunked・HTTP/2 で `Content-Length` の無いもの）と、上限より大きい本文は、読まずに止める。読み終わるまで待つと、終わらない本文（送りながら応答を受ける通信）の要求が、パネルに出ないまま止まり続けるため。読んでいない本文は、パネルで書き換えられず（その旨を出す）、流すと、そのまま行き先に送られる。
- **書き換えて流す**：書き換える欄は、送り直し（#410）の欄を使う。下書きの作り方・確かめ方（メソッド・URL・ヘッダーの形、`Host`・`Content-Length` の扱い、つなぐ先）も同じ（`Proxy.prepare`）。違うのは送ったあと：書き換えた要求は、元の要求の代わりに行き先へ行き、応答はページやプログラムに返る。記録は同じ行のまま、書き換えたあとの要求になり（何が行き先に届いたかを残す）、`edited` の印が付く（一覧の `✎`）。書き換える前の要求は残さない。
- **捨てる**：行き先に送らず、クライアントに 502（`kisui proxy: the request was dropped in the proxy panel`）を返す。接続を切るのではなく応答を返すのは、接続を切られたブラウザやプログラムが、同じ要求を自動で送り直すことがあるため（送り直された要求が、また止まる）。記録は `failed` で、理由に捨てたことを残す。
- **待ちすぎたとき**：プロキシの側には、止めている時間の上限を付けない（上限で勝手に流すと、止めて確かめたい要求が、見ていない間に行き先に届く。上限で捨てると、パネルを見ている途中の要求が消える）。待つのをやめるのはクライアントの側：ページやプログラムが、自分の時間切れで切ったら、その通信は `failed`（理由に、止めている間にクライアントが待つのをやめたこと）になる。ただし、HTTP/1.1 の、本文を読まずに止めた要求（上の「本文」）は、クライアントが切っても気づけず、「止めている」のまま残る（Go の `net/http` のサーバーは、HTTP/1.1 では、要求の本文を読み終えるまで、接続が切れたのを見張らない。動かして確かめた。HTTP/2 は気づく）。残った行は、流す・捨てるか、止めるのをやめれば片付く（流すと、切れた接続に気づいて `failed` になる）。
- **止めたまま、決める相手がいなくならないようにする**：止めている要求は、パネルでしか流せない。パネルが見えない・Dialog がいない間も止め続けると、ページやコマンドが、理由の見えないまま待つ。そこで、次のときは止めるのをやめる。待ち受け口が残るときは、止めていた要求をそのまま流し、待ち受け口を閉じるときは、接続ごと切る。
  - パネルを閉じたとき（`x c`・`q`）：そのまま流す。入れるときは逆に、パネルが閉じていれば開く。
  - ターミナルのタブを通すのをやめたとき（`x s`）：そのまま流す（待ち受け口は、中継だけを続ける）。
  - Window の接続が切れたとき（Dialog を閉じた・ssh が切れた）：そのまま流す。`kisui serve` は Dialog がいなくても動き続け、ターミナルのタブのペインも残るので、`kisui serve` の側でやめる（`proxyManager.releaseHolds`）。
  - 待ち受け口を閉じるとき（`Proxy.Close`）：止めていた要求は、応答を返さずに接続ごと切る（記録の理由は、プロキシを閉じたこと）。ブラウザのタブを通すのをやめたとき（`x s`。ページは、プロキシ無しで読み直される）、タブ（ワークスペース）を閉じたとき、`kisui serve` を終えるとき・引き継ぐとき（版を上げたとき。入れていたことは次の serve に渡さない）。流さないのは、待ち受け口を閉じると、通している最中のほかの接続も切れるので、止めていた要求だけを行き先に送っても、応答を返す先が無いため。何も答えずに戻ると、Go の `net/http` が中身の無い 200 を返す（行き先に送っていない要求が成功に見える）ので、接続を切る。
  - 待ち受け口が残るときに「そのまま流す」を選んだのは、止めるのを入れる前の動き（何もせずに通す）に戻すのが、ページやコマンドにとっていちばん驚きが少ないため。捨てる方に倒すと、Dialog を閉じただけで、動いているコマンドの通信が失敗する。
  - ほかのタブを出している間は、止めたまま（タブごとの切り替えなので）。サイドバーのタブの行の「プロキシ」の札は出ているが、止めていることを示す札は入れていない。
- **パネルの動き**：要求が止まると、止めている要求を選んでいなければ、その行を選ぶ（すぐに決められるように。書き換えている間は選び直さない）。流す・捨てると、次に古い、止めている要求を選ぶ（止めた順に `f` を続けて押せる）。無ければ、そのままにして、流したものは応答の側を出す。止めている要求を選んでいる間は、中身の上に、流す・書き換える・捨てるのボタンを出す。
- **同時に止める数**：1 つのプロキシで 100 まで。超えた要求は、空くまで待つ（記録には出ない。止めずに流しはしない）。止めている通信は、記録の上限（1000 件・64 MiB）を超えても捨てない（捨てると、パネルから流せなくなる）。
- **古い `kisui serve`**：`capabilities` の `"proxy.hold"` で見分け、無ければ「古い版」と知らせる。
- **信頼の範囲**：`proxy.hold`・`proxy.release` は、ほかの `proxy.*` と同じく、Dialog とつながった（`session.hello` を済ませた）接続からだけ受ける。書き換えた要求の確かめ方は `proxy.resend` と同じ（プロキシ自身の待ち受け口を指す要求は断る）。
