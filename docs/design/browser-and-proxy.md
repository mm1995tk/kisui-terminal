# ブラウザの埋め込みと Web プロキシ（設計）

Issue #15 の検討結果。方式を決め、実装は個別の Issue に分ける。

> **内蔵ブラウザ（ブラウザタブ）は #116 で外した。** GUI にはブラウザのペインを足したが（#556）、#96 で外した（末尾の「GUI の外部ブラウザ」）。TUI に残っているのはポート転送（`:browser forward`）と外部ブラウザ連携だけ（`:open-url` と `Space o` は shijimi-editor から外した。mm1995tk/shijimi-editor#646）。理由は末尾の「内蔵ブラウザを外した理由」。**GUI の内蔵ブラウザは #202 で、ペインではなくワークスペースのタブの形で入れ直した**（末尾の「GUI の内蔵ブラウザ（#202。入れ直し）」）。この文書の他の部分は、当時の検討の記録として残す。

## 結論

- Web ページは **ヘッドレス Chromium でスクリーンショットを撮り、既存の画像ビュー（`core/image.go`、描くのは `ui/tui/image_draw.go`）で表示する**。
- 同じ仕組みを #14（mermaid プレビュー）と共有する。
- リモート環境（VM）向けに、**shijimi に組み込みの HTTP リバースプロキシ**を持つ。手元のブラウザからは SSH のポート転送（`ssh -L`）で見る。
- 外部ブラウザ連携（`xdg-open` / `open`）を、最初に作る最小の手段とする。

## 検討した方式

### 描画方式

| 方式                          | 長所                                                                  | 短所                                            | 判断                 |
| ----------------------------- | --------------------------------------------------------------------- | ----------------------------------------------- | -------------------- |
| テキスト化（w3m / lynx 風）   | 依存なし、軽い                                                        | JS を実行できない。SPA の開発サーバーは空になる | 採用しない           |
| 画像化（ヘッドレス Chromium） | JS 込みで正しく描画できる。画像ビューを再利用できる。#14 と共有できる | Chromium が必要。操作は再撮影になる             | **採用**             |
| 外部ブラウザ連携              | 実装が小さい。完全な機能                                              | 端末の外に出る。リモートでは使えない            | 最初の一手として採用 |

画像化はハーフブロック描画のため解像度が低い。読み取り用途は外部ブラウザ連携で補う。
Kitty graphics protocol による高解像度表示と動画の再生は、Chromium を常駐させる方式として別に実装した（#57、下の「ライブ表示」）。Sixel 対応は扱っていない。

### プロキシの形

- shijimi が `127.0.0.1:<ポート>` で待ち受け、`localhost:<対象ポート>` へ転送する。
- 転送先は `:browser forward <対象ポート> [待ち受けポート]` で追加する。
- リモートの VM で shijimi を動かしている場合、手元で `ssh -L <手元ポート>:127.0.0.1:<待ち受けポート> vm` を実行すると、手元のブラウザで見られる。
- 公開インターフェース（`0.0.0.0`）には既定でバインドしない。

#### 直接の `ssh -L` に対してプロキシが足すもの

`ssh -L <手元ポート>:127.0.0.1:<対象ポート> vm` と直接書けば、転送だけならプロキシ無しでできる。プロキシを持つ理由は次の 3 つ。

1. **待ち受けポートを固定できる。** 開発サーバーのポートが変わっても、`ssh -L` とブラウザビューの URL は変えずに済む。
2. **ブラウザビューの URL を一本化できる。** エディタ内のブラウザビュー（#36）は常に待ち受けポートを参照する。
3. **`::1`（IPv6）にしか bind しないサーバーを、`127.0.0.1`（IPv4）で受けられる。**

この 3 つが不要な場合は、`ssh -L` を直接使えばよい。#37 はこの範囲に絞る（転送だけの機能は作らない）。

## 後から変えられるようにする点

- ブラウザの実行ファイルのパスは設定（`config.toml` の `[browser]` の `chromium`）で上書きできるようにする。
- 描画バックエンドは `Renderer` インターフェースの裏に置く。Chromium 以外に差し替えられる。
- プロキシの待ち受けアドレスは設定で変えられるようにする。
- **設定の置き場所:** `[browser]` セクションは `~/.config/shijimi-editor/config.toml` か `.shijimi-editor/config.toml` にのみ書く。README に明記する。

## ライブ表示（Issue #57）

Kitty graphics protocol に対応した端末（Kitty / Ghostty / WezTerm）では、静止画の代わりに常駐 Chromium の画面を流す。

- **画像の配置:** Unicode placeholder（U+10EEEE + 行・列の結合文字、前景色が画像 ID）。画像データは端末へ直接送り、bubbletea が描くのはセルの文字だけにする。差分描画や、パレットなどの重ね描きと衝突しない。
- **書き込みの直列化:** bubbletea の出力（`tea.WithOutput`）と画像の送信は同じ `kitty.Writer` を通し、エスケープシーケンスが混ざらないようにする。応答が stdin に返らないよう `q=2` を付ける。
- **Chromium:** `internal/cdp` が chromedp で常駐させ、`Page.startScreencast`（JPEG、quality 70）でフレームを受け取り、Go 側でデコードして zlib 圧縮の RGB（Kitty の `f=24,o=z`）で端末へ送る。PNG は動画で 1 枚数 MB になり SSH 越しで詰まるため使わない。フレームは最新の 1 枚だけ保持し、最大 15 fps で端末へ送る。端末が遅いときは映像がコマ落ちするだけで、遅延は溜まらない。
- **表示中だけ送る:** 別のタブが前にあるときは screencast を止める。再表示で最新のフレームを送り直す。
- **入力:** マウスは、画像内の相対位置からページの座標へ変換して `Input.dispatchMouseEvent` で送る（セルのピクセルサイズに依存しない）。キーは入力モードのときだけ送る。
- **viewport:** セル数 × セルのピクセルサイズ（`TIOCGWINSZ`。取れなければ 10×20）。幅 1600 px・高さ 1000 px を上限に、比率を保って縮める。
- **戻り先:** 非対応端末では従来どおり `render.Renderer` の静止画表示。`render.Renderer` は mermaid プレビューも使うので残す。
- **sandbox:** 無効にしない（#51）。

## 内蔵ブラウザを外した理由（#116）

Chromium を shijimi と同じマシン（多くは SSH 先の VM）で動かし、画面を端末へ送る形には、次の問題があった。

- Herdr の中では、ペインの描き直しで Kitty graphics の画像が消える（#102）。半ブロックの静止画にしても、JS の読み込み前に撮れてしまう。
- SSH 越しでは動画のコマが多すぎる。実測で毎秒約 8 MB を送り、Kitty が受け取りの処理に追われて画面を描けなくなった（#103）。
- 音声は VM で鳴るので、手元まで運ぶ仕組みが別に要る（#104）。

根本から直すには、ブラウザを手元のマシンで動かし、手元に中継プログラムを置いて端末への出力に画像を混ぜる必要がある（terminal-browser の `--ssh` と同じ形）。費用に見合わないため、ブラウザ機能を外し、ポート転送と手元のブラウザで見る形に戻した。

## GUI の外部ブラウザ（#96。内蔵ブラウザのペイン #556 は外した）

GUI には #556 で、Tauri の子の webview でページを出す「ブラウザのペイン」を足したが、#96 で外した。理由は次の通り。

- 見づらく、操作感が良くない。
- パスキー（WebAuthn）が使えない（macOS の WKWebView・Linux の WebKitGTK の制約）。
- Netflix など DRM の動画が再生できない。

動画を小窓で観るのは Safari のピクチャー・イン・ピクチャーで済ませる。ページは手元の外部ブラウザ（OS 既定のブラウザ）で開く。Chromium（CEF）を中に入れることは、しない。

- **開く入口は 3 つ**：shj の URL を開く要求（`ctl.PaneRequest` の `op: "open"`・`kind: "browser"`。shj の PR を開く操作などが使う）、`kisui open <URL>`、ターミナルの URL のクリック（`cmd + click`・`cmd + shift + click`。macOS 以外は ctrl。どちらも同じ）。内蔵ブラウザを有効にしていれば、どれもワークスペースの新しいタブで開く（#203。下の「URL を内蔵ブラウザのタブで開く」）。前の 2 つは `kisui serve` が GUI に `browser.open` を通知し（ペインは作らない。gui-protocol.md の「ブラウザの URL を開く」）、クリックは GUI の中で済む。開くのは殻の `open_url_external`（`app/src-tauri/src/open_url.rs`）で、`open`（macOS）・`xdg-open`（それ以外）に URL を渡す。
- **開いてよい URL**：http と https だけ。ユーザー名とパスワードを含むもの・制御文字を含むもの・長すぎるものは断る（`kisui serve` と殻の両方で確かめる）。
- **リモートのマシンの `localhost`**：ワークスペースのマシンが ssh の先のとき、host が `localhost`・`127.0.0.1`・`[::1]`・`0.0.0.0`・`*.localhost` の URL は、手元の外部ブラウザでそのまま開くと手元の別のマシンに行ってしまう。そこで GUI が `ssh <ホスト> -- <kisui> relay` を張り（#127。`kisui attach` と同じ起こし方で、質問は GUI の窓に出る askpass）、手元の `127.0.0.1:<空きポート>` で待ち受けて、ブラウザの接続を `kisui relay` の上でリモートのポートへ中継する。開くのは `http://127.0.0.1:<空きポート>/…`。`kisui relay` はマシンごとに 1 本、待ち受けはマシンと URL のポートごとに 1 つで、どちらも使い回し、GUI が終わるときに止める（ページを開いたあとも、タブが見続けられるように残す）。待ち受けのポートは、マシンとリモートのポートから決まる番号（20000〜29999。FNV-1a）を先に試し、誰かが答えるか bind できなければ空きポートにする（#203。起動し直しても同じ origin になり、ページの localStorage などが残る。Cookie はポートを区別しないので、もともと残る）。開く前に、そのポートにつながるかを確かめ、誰も待っていなければ開かずに理由を出す。ほかの host は、手元から直接開く。取り決めと窓の側の動きは `relay.md`。
- **`ssh -L` をやめた理由（#127）**：前は `ssh -N -L 127.0.0.1:<空きポート>:localhost:<ポート> <ホスト>` のポート転送で見せていた。`ssh -L` は、つなぎ先の sshd と途中の中継がポート転送を許すときにしか使えない（Cloudflare Zero Trust の Access for Infrastructure・`AllowTcpForwarding no` の sshd・会社の踏み台）。普通の ssh のセッションの標準入出力の上で中継する `kisui relay`（#126）に替え、ターミナルが使える環境なら URL も開けるようにした。`ssh -L` に戻す道は残していない。
- **絶対 URL の localhost**：ページの中のリンクやリダイレクトが絶対 URL の `http://localhost:…` を指すと、転送を通らない（今は対処しない）。
- **設定 `[gui] url_open`**：開き先を内蔵ブラウザか外部ブラウザかから選ぶ設定だったが、選ぶものが無くなったので外した。設定ファイルに残っていても無視し、起動を止めず、間違いとして出さない。

## GUI の内蔵ブラウザ（#202。入れ直し）

#96 で外した理由（上の「GUI の外部ブラウザ」）を、次のように解いて入れ直した。作業（ワークスペース）ごとに、ブラウザのタブを持てる。

- **見づらい**：前はペインを分けて、画面の半分にページを出していた。今は、タブを選ぶとグリッドの場所すべてがそのページになる（ペインは分けない）。#231 以降は、ターミナルのグリッドもタブの 1 つなので、ワークスペースの帯を選んでも、ターミナルのグリッドに戻らない（そのワークスペースが出していたものが出る。ターミナルのタブの行を選べば戻る）。
- **パスキー**：パスキーが要る場面だけ Chrome か Firefox に移って戻る（#206・#207）。設定の `[gui.browser] passkey_sites` に書いたサイトのページがパスキーを求めると、同じ URL を外のブラウザで開き、拡張機能（#207）が送るログインした後の Cookie を内蔵ブラウザに写して、タブを開き直す。取り決めと安全のための作りは `docs/passkey-extension.md`。
- **DRM の動画**：内蔵ブラウザでは再生しない。追加の部品で再生する案は #208 で検討する。
- **CEF**：入れない。OS の WebView（Tauri の子の webview。macOS は WKWebView、Linux は WebKitGTK）を使う。

この Issue（#202）で作ったのは土台だけ。URL を開く入口（`kisui open`・shj の URL を開く要求・URL のクリックから内蔵ブラウザで開く。#203。下の「URL を内蔵ブラウザのタブで開く」）、シークレットのタブ・新しい窓・ダウンロード（#204）、ブックマークなど（#205）、パスキー（#206）は別の Issue。

- **有効にする**：GUI の設定ファイル（`$XDG_CONFIG_HOME/kisui-terminal/config.toml`。`config.local.toml` が上に重なる）に `[gui.browser]` `enabled = true` と書いた人にだけ出す。書いていなければ、リーダーの `o` のグループもサイドバーのタブも出ず、何も変わらない。
- **タブ**：タブは GUI のワークスペース（`docs/design/gui-protocol.md` の「ワークスペース」。#231）に属し、サイドバーのワークスペースの帯の下に、ターミナルのタブと一緒に開いた順に並ぶ（「タブ N」で畳める。リーダーの `o z`）。どのワークスペースにも属さないタブは作らない。ワークスペースを閉じると、その下のタブも閉じる。タブには名前を付けられ（リーダーの `o R`）、付けた名前を 1 行目に出し、ページの題は出さない（空にするとページの題に戻る）。ブラウザのタブにマシンは出さない（ページを表示するのは手元の PC）。タブは、開いたときのターミナルのタブのマシンを覚える（#203 のリモートの `localhost` の中継で使う）。
- **favicon**（#237）：サイドバーのブラウザのタブの行の頭に、ページの favicon を出す（取れないとき・読み込み中は地球のアイコン）。ページの読み込みが終わったとき・（読み込みの後に）題が変わったときに、殻がページの中で `browser_favicon.js` を動かして読む（`app/src-tauri/src/favicon.rs`）。動かすのはページの外の世界（isolated world。Linux は WebKitGTK の `call_async_javascript_function` の world、macOS は `WKContentWorld`）で、ページのスクリプトからは見えず、DOM の関数を差し替えられても効かない。殻から呼んで答えを受けるので、ページが偽の知らせを送る口は無い（キーの知らせのような `window.open` の URL は使わない。Linux の WebKitGTK は、ユーザーの操作の無い `window.open` を止めるため）。スクリプトは `<link rel="icon">`（32×32 か SVG を先に）、`apple-touch-icon`、`/favicon.ico` の順に、ページの中で読み込み、32×32 の PNG の data: URL にして返す。読み込むのはページ自身（ページと同じデータ。シークレットのタブはディスクに残さないデータ）で、殻とメインの webview はネットワークに出ない。外の origin の画像は CORS で許されたものだけ読める（許されなければ次の候補）。殻は答えの形（PNG の data: URL・base64 の文字・64 KB まで）を確かめてから画面に渡す（`browser-favicon`）。読み込みが始まったら・新しく頼んだら、それまでに頼んだ答えは捨てる（後から届いた古い答えで上書きしない）。読み込み中は頼まない（macOS では、読み込みが途中で失敗する・止められると、wry が読み込みの終わりを知らせないので、次の読み込みが終わるまで地球のアイコンのまま）。favicon は覚えない（`browser-tabs.json` に書かない。シークレットのタブの favicon をディスクに残さないため。再起動の後は、ページを読み込めばまた出る）。新しいタブのページ・ブックマークには出さない。
- **子の webview**：タブごとに 1 つ、初めて出すときに作る（`app/src-tauri/src/browser.rs`。Tauri の `unstable` の `Window::add_child`）。グリッドは今のワークスペースの分しか描かないので、ほかのワークスペースに移る・グリッドに戻るときは隠すだけで、ページは残す。出す場所は画面（`app/src/browser/BrowserArea.tsx`）が決め、毎フレーム見て、変わったときだけ殻に送る。
- **上に出るものとの重なり**：子の webview は画面（DOM）より上に重なる。ダイアログを出している間はページを隠す。右下のお知らせ（閉じるまで残り、後ろの画面を触れたままにするため）・ページ内検索の欄・トーストが重なるときは、ページの下の端をそれの上まで上げる（縦だけ縮める。横に縮めると、ページの組み直しで読んでいた所を見失うため）。低くなりすぎるなら隠す。リーダーの案内・右クリックのメニュー（浮かべるもの）は、macOS ではページを縮めず、画面（メインの webview。ページの場所の背景を透明にしてある）をページの webview より前に出して（同じ窓への `reparent`。`browser_layer`）ページの上に重ねる。ページはすりガラスのように見え（半透明の色をかぶせる。CSS の `backdrop-filter` は別の webview をぼかせない）、動画と音は止まらないが、マウスでもキーでも操作できない。重なりが消えたらページを前に戻す。Linux と Windows は、浮かべるものも縮めて避ける（`app/src/browser/overlay.ts`）。
- **キー**：リーダーの `o` のグループ（`docs/key-design.md` の 3.2）。ブラウザを出している間は、Cmd+R / Ctrl+Shift+R がページを読み込み直す（ほかのときはリサイズモード）。ブラウザの操作は場所のキーにしない。ページの中のキー（GitHub の `t`・`?` など）は、ページに渡す。
- **ページにキーがあるときのリーダー**：ページにキーがあると、画面の `window` の `keydown` には届かない。そこで、ページに入れるスクリプト（`browser_keys.js`。どのフレームにも入れる）が、リーダーと近道に当たるキーだけを止めて、`kisui-key:` の URL を `window.open` で開こうとする。殻の `on_new_window` がそれを受けて開かずに断り、キーを画面に知らせてから、キーをメインの webview に移す。リーダーとグループの入口のあとは、キーが移るまでの短い間（1.5 秒か、ページからキーが外れるまで）のキーも同じように渡す（速く打った続きのキーがページに届かないように）。操作が終わり（リーダーなら出て）、画面のキーの行き先がそのままなら、キーをページに戻す。遷移（URL の書き換え）ではなく `window.open` にしたのは、ページの `beforeunload` を起こさないため。Tauri のアプリのメニューのアクセラレータで受ける形は、Linux にメニューバーが無く、使わなかった。
- **macOS の矢印キーの豆腐**：macOS の子の webview（`add_child`）は、カーソルが動けない方向に矢印キーを押すと、矢印キーに使う私用領域の文字（U+F700〜）をテキストとして入力してしまう（tauri-apps/tauri#10194。空の入力欄では毎回）。殻には手を入れず、同じ `browser_keys.js` が `beforeinput`（`insertText`）で U+F700〜U+F74F（AppKit の関数キーの文字の区画。U+F8FF の Apple のロゴは打てるよう止めない）を含む入力だけを止める。`keydown` は止めないので、カーソルの移動もページの矢印キーの処理も変わらない。
- **ページに Tauri の命令を使わせない**：子の webview は外の URL（`WebviewUrl::External`）で、tauri は `remote` を持つ capability の無い外の URL からの IPC を断る。capability はメインの webview にだけ与える（`capabilities/default.json` は `webviews: ["main"]`。`windows: ["main"]` にすると、同じ窓に置く子の webview にも当たる）。殻の命令は、呼んだ webview が `main` かも確かめる（`from_main`）。キーを知らせる URL には、webview を作るたびに決める nonce を入れ、合わないものは捨てる。nonce はスクリプトの関数の中にだけ置き、使う組み込みの関数は先に取っておくので、ページのスクリプトはキーを真似できない（`isTrusted` でないキーも渡さない）。真似できても、できるのはリーダーと近道を押すことまで。
- **遷移と新しい窓**：子の webview の遷移は http・https・about だけ許す。新しい窓（`target=_blank`・`window.open`）は、下の「シークレットのタブ・新しい窓・ダウンロード（#204）」。
- **ログインとタブを残す**：ログイン（Cookie などのページのデータ）は、すべてのタブで 1 つを共有し、ディスクに残す。Linux はデータのフォルダ（`~/.local/share/dev.mm1995tk.kisui-terminal`）の `browser/`、macOS は WKWebView の既定の置き場（`~/Library/WebKit/dev.mm1995tk.kisui-terminal` など。場所は OS が決める）。開いていたタブ（開いたときのターミナルのタブと URL と題）は、データのフォルダの `browser-tabs.json`（自分だけが読めるファイル）に覚え、再起動したら戻す（どのワークスペースもターミナルのタブから始め、ページはタブを出したときに読み込む）。どのワークスペースのタブか、タブの名前、畳んだ印は、GUI のワークスペースの記録（webview の localStorage）が持つ。設定のフォルダには書かない。


## シークレットのタブ・新しい窓・ダウンロード（#204）

- **シークレットのタブ**：リーダーの `o N`。タブごとに別の、ディスクに残さないデータを使う（tauri の `incognito`。Linux は WebKitGTK の ephemeral な WebContext、macOS は WKWebsiteDataStore の nonPersistent）。共有のログインも、ほかのシークレットのタブのログインも見えない。閉じるとログインは消え、`browser-tabs.json` にも書かない（再起動しても戻さない）。サイドバーの行に「シークレット」の札を付ける。パスキーを外のブラウザに移す仕組み（#206）は使わない（パスキーのスクリプトを入れない）。写した Cookie は外のブラウザに残り、「残さない」と食い違うため。パスワードと認証アプリのコードでのログインはできる。
- **新しい窓**：ページが開く新しい窓（`target=_blank` のリンク・`window.open`）は、開いた元のタブと同じワークスペースの新しいタブにして出す。開いた元のページとの連絡（`window.opener`）を保つため、WebKit が求める形で webview を作り、`on_new_window` から `NewWindowResponse::Create` で返す（Linux は元の webview に関係付けた webview（related view。データも元と同じ）、macOS は WebKit が渡した設定で作った webview）。tauri の `Create` は「窓の最初の webview」しか受けないので、隠した窓に子の webview として作って返し、返したあとメイン窓に移して（`Webview::reparent`）、隠した窓を壊す。そのあと画面に知らせ（`browser-popup`）、画面はタブを足す（webview はもうあるので作らない）。データは開いた元と同じなので、シークレットのタブから開いたタブはシークレット（覚えない）。開いたタブは、ふつうのタブと同じく覚える（再起動したら、開いた元との連絡の無いふつうのタブとして戻る）。新しいタブを作れなければ、今まで通り同じタブで開く。ページが `window.open` を繰り返してもタブを増やし続けないよう、1 つのタブ（と、そこから開いた新しいタブすべて）が新しい窓を開けるのは、合わせて 10 秒の間に 5 つまでにし、超えた分は断る（macOS の WKWebView は、ユーザーの操作の無い `window.open` も既定で通すため。Linux の WebKitGTK は既定で止める）。macOS では、WebKit が渡す設定がスクリプトの入れ物（`WKUserContentController`）を開いた元と共有するので、新しいタブにはスクリプトを足さず、開いた元のタブと同じ nonce で知らせを受ける。
- **ページが自分を閉じる**：`window.close()` で、タブを閉じ、開いた元のタブ（同じワークスペースにあれば）に戻る。Linux は WebKitGTK の `close` を直接受ける（wry は webview を壊すだけで殻に知らせないため。`webkit2gtk` を直接使う）。macOS は wry が `webViewDidClose` を受けないので、ページに入れるスクリプト（`browser_close.js`。上のフレームだけ）が `window.close` を差し替え、キーと同じ形（`kisui-close:` の URL と nonce）で殻に知らせる。閉じてよいのは、ふつうのブラウザと同じく、ほかのページが開いた窓か、履歴が 1 つだけのページ。
- **ダウンロード**：OS のダウンロードのフォルダ（tauri の `download_dir`。ふつうは `~/Downloads`）に、場所を聞かずに保存する（`app/src-tauri/src/download.rs`）。名前はページが勧めたものの最後の部分（フォルダの区切りと制御文字を除く）で、同じ名前があれば `名前 (1).拡張子` `名前 (2).拡張子` … と番号を付ける（wry と同じ付け方）。終わったら右下のお知らせで知らせ（`browser-download`）、「開く」（OS の既定のアプリ）と「フォルダを表示」（macOS は Finder でファイルを選んだ状態、Linux はフォルダを開く）ができる。キーはリーダーの `n o` `n f`（いちばん新しいダウンロード）。開く・表示するのは殻が保存したファイルだけ（画面は番号で頼み、パスは渡さない）。Linux のダウンロードは WebContext（データの単位）に届くので、WebContext ごとに 1 度だけ受け口を足す（wry の受け口は webview ごとに足すので、共有のデータを使うタブの数だけ重なり、最初のタブを閉じると断るようになる）。macOS は webview ごとに受ける（tauri の `on_download`。終わったときにパスが来ないので、始めたときに覚える）。
## URL を内蔵ブラウザのタブで開く（#203）

内蔵ブラウザを有効にした人が、ターミナルに出た URL や `kisui open` の URL を、作業中のワークスペースのタブで開けるようにした。無効なら、今まで通り外部ブラウザで開く。

- **入口**：`kisui open <URL>` と shj の URL を開く要求（どちらも通知 `browser.open` `{workspaceId, url}`）は、そのワークスペースの新しいタブで開く。ターミナルの URL の `cmd + click`・`cmd + shift + click`（macOS 以外は ctrl）は、今のワークスペースの新しいタブで開く（`app/src/App.tsx` の `openUrlFor`・`openInNewTab`）。開いたタブを出し、今のワークスペースならページにキーを向ける。ほかのワークスペースの通知なら、そこへは移らない（`pane.show` と同じ。そのワークスペースに移ると、タブのページが出ている）。取り決め（`kind: "browser"`）そのものは変えていない。
- **外部ブラウザで開くクリック**：`cmd + option + click`（macOS 以外は `ctrl + alt + click`）。`shift` を足しても同じ（マウスの報告を有効にしたアプリが動いている間は、`shift` 付きのクリックだけが GUI に届くため）。`cmd + shift + click` は「マウスを使うアプリが動いていても開く」意味のまま残した。開いたページを外部ブラウザに移すのは、今まで通りリーダーの `o e`。
- **キーでは開かない**：画面の URL をキーで選んで開く操作は作らない。
- **リモートのマシンの `localhost`**：外部ブラウザと同じ `kisui relay` の中継（上の「GUI の外部ブラウザ」・relay.md）を通す。殻の命令 `browser_resolve_url`（`open_url.rs`）が中継を用意して、タブに開かせる手元の URL（`http://127.0.0.1:<手元のポート>/…`）を返す。誰も待っていなければ、タブを作らずに理由を出す（外部ブラウザと同じ）。タブが覚えて入力欄に出すのは中継前の元の URL で、ページの遷移で殻から届く中継の URL は、同じ origin なら元の origin に戻してから書く（`app/src/browser/relay.ts`）。戻る・進むで前の中継の URL に戻ることもあるので、対応はタブごとにこれまで使ったものを全部覚え、タブを閉じたときに捨てる。再起動して戻したタブも、出すときに改めて中継を用意する。ページの中の絶対 URL の `http://localhost:…` が中継を通らないのは、外部ブラウザと同じ（今は対処しない）。
- **待ち受けのポート**：起動し直しても同じ番号になりやすくした（上の「リモートのマシンの `localhost`」）。ページの origin（`127.0.0.1:<ポート>`）が起動のたびに変わると、localStorage などが起動のたびに別になるため。
