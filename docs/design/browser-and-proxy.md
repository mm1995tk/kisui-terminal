# ブラウザの埋め込みと Web プロキシ（設計）

Issue #15 の検討結果。方式を決め、実装は個別の Issue に分ける。

> **内蔵ブラウザ（ブラウザタブ）は #116 で外した。** GUI にはブラウザのペインを足したが（#556）、#96 で外した（末尾の「GUI の外部ブラウザ」）。TUI に残っているのはポート転送（`:browser forward`）と外部ブラウザ連携（`:open-url`）だけ。理由は末尾の「内蔵ブラウザを外した理由」。この文書の他の部分は、当時の検討の記録として残す。

## 結論

- Web ページは **ヘッドレス Chromium でスクリーンショットを撮り、既存の画像ビュー（`core/image.go`、描くのは `ui/tui/image_draw.go`）で表示する**。
- 同じ仕組みを #14（mermaid プレビュー）と共有する。
- リモート環境（VM）向けに、**shijimi に組み込みの HTTP リバースプロキシ**を持つ。手元のブラウザからは SSH のポート転送（`ssh -L`）で見る。
- 外部ブラウザ連携（`xdg-open` / `open`）を、最初に作る最小の手段とする。

## 検討した方式

### 描画方式

| 方式                          | 長所                                                                  | 短所                                            | 判断                 |
| ----------------------------- | --------------------------------------------------------------------- | ----------------------------------------------- | -------------------- |
| テキスト化（w3m / lynx 風）   | 依存なし、軽い                                                        | JS を実行できない。SPA の開発サーバーは空になる | 採用しない           |
| 画像化（ヘッドレス Chromium） | JS 込みで正しく描画できる。画像ビューを再利用できる。#14 と共有できる | Chromium が必要。操作は再撮影になる             | **採用**             |
| 外部ブラウザ連携              | 実装が小さい。完全な機能                                              | 端末の外に出る。リモートでは使えない            | 最初の一手として採用 |

画像化はハーフブロック描画のため解像度が低い。読み取り用途は外部ブラウザ連携で補う。
Kitty graphics protocol による高解像度表示と動画の再生は、Chromium を常駐させる方式として別に実装した（#57、下の「ライブ表示」）。Sixel 対応は扱っていない。

### プロキシの形

- shijimi が `127.0.0.1:<ポート>` で待ち受け、`localhost:<対象ポート>` へ転送する。
- 転送先は `:browser forward <対象ポート> [待ち受けポート]` で追加する。
- リモートの VM で shijimi を動かしている場合、手元で `ssh -L <手元ポート>:127.0.0.1:<待ち受けポート> vm` を実行すると、手元のブラウザで見られる。
- 公開インターフェース（`0.0.0.0`）には既定でバインドしない。

#### 直接の `ssh -L` に対してプロキシが足すもの

`ssh -L <手元ポート>:127.0.0.1:<対象ポート> vm` と直接書けば、転送だけならプロキシ無しでできる。プロキシを持つ理由は次の 3 つ。

1. **待ち受けポートを固定できる。** 開発サーバーのポートが変わっても、`ssh -L` とブラウザビューの URL は変えずに済む。
2. **ブラウザビューの URL を一本化できる。** エディタ内のブラウザビュー（#36）は常に待ち受けポートを参照する。
3. **`::1`（IPv6）にしか bind しないサーバーを、`127.0.0.1`（IPv4）で受けられる。**

この 3 つが不要な場合は、`ssh -L` を直接使えばよい。#37 はこの範囲に絞る（転送だけの機能は作らない）。

## 後から変えられるようにする点

- ブラウザの実行ファイルのパスは設定（`config.toml` の `[browser]` の `chromium`）で上書きできるようにする。
- 描画バックエンドは `Renderer` インターフェースの裏に置く。Chromium 以外に差し替えられる。
- プロキシの待ち受けアドレスは設定で変えられるようにする。
- **設定の置き場所:** `[browser]` セクションは `~/.config/shijimi-editor/config.toml` か `.shijimi-editor/config.toml` にのみ書く。README に明記する。

## ライブ表示（Issue #57）

Kitty graphics protocol に対応した端末（Kitty / Ghostty / WezTerm）では、静止画の代わりに常駐 Chromium の画面を流す。

- **画像の配置:** Unicode placeholder（U+10EEEE + 行・列の結合文字、前景色が画像 ID）。画像データは端末へ直接送り、bubbletea が描くのはセルの文字だけにする。差分描画や、パレットなどの重ね描きと衝突しない。
- **書き込みの直列化:** bubbletea の出力（`tea.WithOutput`）と画像の送信は同じ `kitty.Writer` を通し、エスケープシーケンスが混ざらないようにする。応答が stdin に返らないよう `q=2` を付ける。
- **Chromium:** `internal/cdp` が chromedp で常駐させ、`Page.startScreencast`（JPEG、quality 70）でフレームを受け取り、Go 側でデコードして zlib 圧縮の RGB（Kitty の `f=24,o=z`）で端末へ送る。PNG は動画で 1 枚数 MB になり SSH 越しで詰まるため使わない。フレームは最新の 1 枚だけ保持し、最大 15 fps で端末へ送る。端末が遅いときは映像がコマ落ちするだけで、遅延は溜まらない。
- **表示中だけ送る:** 別のタブが前にあるときは screencast を止める。再表示で最新のフレームを送り直す。
- **入力:** マウスは、画像内の相対位置からページの座標へ変換して `Input.dispatchMouseEvent` で送る（セルのピクセルサイズに依存しない）。キーは入力モードのときだけ送る。
- **viewport:** セル数 × セルのピクセルサイズ（`TIOCGWINSZ`。取れなければ 10×20）。幅 1600 px・高さ 1000 px を上限に、比率を保って縮める。
- **戻り先:** 非対応端末では従来どおり `render.Renderer` の静止画表示。`render.Renderer` は mermaid プレビューも使うので残す。
- **sandbox:** 無効にしない（#51）。

## 内蔵ブラウザを外した理由（#116）

Chromium を shijimi と同じマシン（多くは SSH 先の VM）で動かし、画面を端末へ送る形には、次の問題があった。

- Herdr の中では、ペインの描き直しで Kitty graphics の画像が消える（#102）。半ブロックの静止画にしても、JS の読み込み前に撮れてしまう。
- SSH 越しでは動画のコマが多すぎる。実測で毎秒約 8 MB を送り、Kitty が受け取りの処理に追われて画面を描けなくなった（#103）。
- 音声は VM で鳴るので、手元まで運ぶ仕組みが別に要る（#104）。

根本から直すには、ブラウザを手元のマシンで動かし、手元に中継プログラムを置いて端末への出力に画像を混ぜる必要がある（terminal-browser の `--ssh` と同じ形）。費用に見合わないため、ブラウザ機能を外し、ポート転送と手元のブラウザで見る形に戻した。

## GUI の外部ブラウザ（#96。内蔵ブラウザのペイン #556 は外した）

GUI には #556 で、Tauri の子の webview でページを出す「ブラウザのペイン」を足したが、#96 で外した。理由は次の通り。

- 見づらく、操作感が良くない。
- パスキー（WebAuthn）が使えない（macOS の WKWebView・Linux の WebKitGTK の制約）。
- Netflix など DRM の動画が再生できない。

動画を小窓で観るのは Safari のピクチャー・イン・ピクチャーで済ませる。ページは手元の外部ブラウザ（OS 既定のブラウザ）で開く。Chromium（CEF）を中に入れることは、しない。

- **開く入口は 3 つ**：shj の `:open-url`（`Space o`）、`kisui open <URL>`、ターミナルの URL のクリック（`cmd + click`・`cmd + shift + click`。macOS 以外は ctrl。どちらも同じ）。前の 2 つは `kisui serve` が GUI に `browser.open` を通知し（ペインは作らない。gui-protocol.md の「ブラウザの URL を開く」）、クリックは GUI の中で済む。開くのは殻の `open_url_external`（`app/src-tauri/src/open_url.rs`）で、`open`（macOS）・`xdg-open`（それ以外）に URL を渡す。
- **開いてよい URL**：http と https だけ。ユーザー名とパスワードを含むもの・制御文字を含むもの・長すぎるものは断る（`kisui serve` と殻の両方で確かめる）。
- **リモートのマシンの `localhost`**：ワークスペースのマシンが ssh の先のとき、host が `localhost`・`127.0.0.1`・`[::1]`・`0.0.0.0`・`*.localhost` の URL は、手元の外部ブラウザでそのまま開くと手元の別のマシンに行ってしまう。そこで GUI が `ssh -N -L 127.0.0.1:<空きポート>:localhost:<ポート> <ホスト>` を張り（`ExitOnForwardFailure=yes`。質問は GUI の窓に出る askpass）、`http://127.0.0.1:<空きポート>/…` を開く。転送はマシンと URL のポートごとに 1 本で、生きていれば使い回し、GUI が終わるときに止める（ページを開いたあとも、タブが見続けられるように残す）。ほかの host は、手元から直接開く。
- **ポート転送が使えないとき**：`ssh -L` は、つなぎ先の sshd と途中の中継がポート転送を許すときにしか使えない。普通の ssh のセッションの標準入出力の上で中継する `kisui relay` を足した（#126。取り決めは `relay.md`）。GUI の側で使うのは別の Issue。
- **絶対 URL の localhost**：ページの中のリンクやリダイレクトが絶対 URL の `http://localhost:…` を指すと、転送を通らない（今は対処しない）。
- **設定 `[gui] url_open`**：開き先を内蔵ブラウザか外部ブラウザかから選ぶ設定だったが、選ぶものが無くなったので外した。設定ファイルに残っていても無視し、起動を止めず、間違いとして出さない。
