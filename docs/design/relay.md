# kisui relay（リモートのマシンの localhost への中継）

Issue #126・#127。リモートのマシンのターミナルで出た `http://localhost:<ポート>` を手元のブラウザで開くのに、前は窓が `ssh -N -L` でポート転送を張っていた。ポート転送は、つなぎ先の sshd と途中の中継が許すときにしか使えない（Cloudflare Zero Trust の Access for Infrastructure・`AllowTcpForwarding no` の sshd・会社の踏み台など）。そこで、普通の ssh のセッションの標準入出力の上で中継する `kisui relay` を置き（#126）、窓はそれだけを使う（#127。`ssh -L` は外した）。ターミナルが使える環境なら URL も開ける。

この文書は、窓の Rust の側と `kisui relay` の間の取り決め。窓の画面（TypeScript）と `kisui serve` の取り決め（`gui-protocol.md`）とは別で、`kisui relay` は `kisui serve` を介さない。窓の側で使うのは別の Issue。

## 起こし方

窓が `ssh <マシン> -- <kisui> relay` で起こす。`<kisui>` は `kisui attach` と同じ探し方で、窓と同じ版をキャッシュに置いたもの。1 本の `kisui relay` の上で、複数の TCP 接続を同時に中継する（ブラウザは 1 つのページで何本も接続を張る）。

`kisui relay` は、標準入力が終わったら（ssh が切れたら）開いている接続をすべて閉じて、終了コード 0 で終わる。取り決めに反する入力（壊れた枠など。下の「中継ごと止める誤り」）では、理由を標準エラー出力に書いて、終了コード 1 で終わる。

## 始まりの目印と版

`kisui relay` は、起動するとまず標準出力に次の 1 行を書く。

```
@@kisui-relay 1@@
```

ログインシェルが motd などを標準出力に出すことがあるので、窓はこの行より前のバイトを捨てる（`kisui attach` の `@@shj-rpc 1@@` と同じ考え方）。この行のあとは、すべて枠。

数字は取り決めの版。枠の形や意味を変え、前の版と話せなくなったら上げる。窓は、知らない版を見たら中継を使わない（`kisui relay` を止め、URL を開くのを、版が違うという理由を付けて失敗にする。`ssh -L` に戻す道は無い）。窓から `kisui relay` へは挨拶を送らない。起こすのは窓で、窓と同じ版の kisui を選んで起こすので、版が違うのは古い kisui が残っているときくらいで、その判断は窓の側だけでできる。

## 枠の形

長さ付きのバイナリの枠。数はすべてビッグエンディアン。

| 位置 | 大きさ | 中身                         |
| ---- | ------ | ---------------------------- |
| 0    | 1      | 種類                         |
| 1    | 4      | 接続の番号（符号なし 32 bit） |
| 5    | 4      | 中身の長さ（最大 65536）     |
| 9    | 長さ   | 中身                         |

1 行 1 メッセージの JSON に base64 で中身を入れる形にしなかったのは、運ぶのが HTTP の本体（画像・動画・JS の束）のバイト列で、base64 で 4/3 倍になり、ssh の上を流れる量と、両側でのエンコードの手間が増えるため。枠の頭は 9 バイトで固定なので、Rust の側でも読み書きが小さく済む。

## 枠の種類

| 値  | 名前   | 向き          | 中身                                       |
| --- | ------ | ------------- | ------------------------------------------ |
| 1   | OPEN   | 窓 → relay    | ポート（2 バイト）と、続けて host（UTF-8） |
| 2   | OPENED | relay → 窓    | なし                                       |
| 3   | DATA   | 両向き        | バイト列                                   |
| 4   | ACK    | 両向き        | 受け取って書き終えたバイト数（4 バイト）   |
| 5   | EOF    | 両向き        | なし                                       |
| 6   | CLOSE  | 両向き        | 理由（UTF-8。空なら正常の終わり）          |

### 接続を開く

- 窓が番号を決めて OPEN を送る。番号は 1 本の `kisui relay` の中で増える一方にし、使い回さない（閉じた接続あての枠が行き違いで届いても、別の接続と取り違えない）。
- つながったら relay が OPENED を返す。つなげなかったら CLOSE を返す（下の理由）。
- 窓は OPENED を待たずに DATA と EOF を送ってよい（つながってから書く）。ブラウザの最初の要求を待たせないため。

### つなぐ先

host は `localhost`・`127.0.0.1`・`::1`（`[::1]` も）だけを受ける。ほかは CLOSE（`denied`）で断る。ポート 0 も断る。前の `ssh -L 127.0.0.1:<手元>:localhost:<ポート>` と同じ範囲で、信頼の境界を広げない。`*.localhost` や `0.0.0.0` の URL を `localhost` に読み替えるのは窓の側の仕事。

`localhost` は、`::1`、`127.0.0.1` の順に試す（IPv6 でつながらなければ IPv4）。`python3 -m http.server` のように IPv4 だけで待つサーバーにもつながる。名前解決（`/etc/hosts`）には頼らない。`localhost` が loopback の外を指すように書き換えられていても、外へは向かわない。

つなぐのを待つのは 10 秒まで。

### データ

DATA の中身は、そのままのバイト列。空の DATA は送らない（受けた側は無視する）。

### 閉じる

- **EOF**: 送った側は、この接続にもう DATA を送らない。TCP の半分の閉じ（書く向きだけを閉じる）にあたる。relay は、窓の EOF を受けたら、受け取った分を書き終えてから TCP の書く向きを閉じる。TCP の先が閉じたら（読みが終わったら）、DATA を送り終えてから EOF を送る。
- **CLOSE**: 接続を捨てる。受けた側は TCP を閉じ、その番号を忘れる。CLOSE に CLOSE は返さない。
- relay は、両向きの EOF が済んだら TCP を閉じて CLOSE（理由は空）を送る。だから、窓が CLOSE を送らない限り、relay から見た接続は必ず CLOSE で終わる。
- 知らない番号（閉じたあとの番号）あての OPENED・DATA・ACK・EOF・CLOSE は、どちらの側も捨てる。CLOSE と行き違いでありうる（窓が CLOSE を送ったあとに、relay の OPENED や DATA が届くことがある）。

CLOSE の理由は、次のどれかで始まり、後ろに `: 詳しいこと` が付くことがある。窓はこれで、ブラウザにどう見せるか（つなげなかったのか、断ったのか）を決められる。

| 理由          | いつ                                                     |
| ------------- | -------------------------------------------------------- |
| （空）        | 正常の終わり                                             |
| `denied`      | loopback 以外の host、ポート 0                           |
| `limit`       | 開いている接続が上限（256）に達している                  |
| `unreachable` | つなげなかった（そのポートで誰も待っていない・時間切れ） |
| `error`       | つないだあとの読み書きの失敗                             |
| `protocol`    | この接続について、取り決めに反する枠が来た               |

## 流量の制御

接続ごと・向きごとに、ACK を待たずに送ってよい量（256 KiB）で制御する。`kisui serve` の `term.ack`（`server/term.go`）と同じ考え方。

- 送る側は、相手が ACK していないバイト数が 256 KiB を超えないように DATA を送る。
- 受ける側は、DATA を自分の先（relay なら TCP、窓ならブラウザの接続）に書き終えたら、そのバイト数を ACK で返す。
- relay は、窓へ送って ACK されていない分が 256 KiB に達したら、TCP を読むのを止める。ブラウザが遅ければ、TCP の先のサーバーが書くのを待たされる。
- relay は、窓から来て TCP に書けていない分を、接続ごとに 256 KiB までしか持たない。窓が ACK を待たずにそれを超えて送ったら、その接続を CLOSE（`protocol`）で閉じる。TCP の先が読まなければ ACK が止まり、窓が送るのを止める。

止まるのはその接続だけで、標準入力の読みとほかの接続は止まらない。`kisui relay` が持つメモリは、接続の数 × 256 KiB で頭打ちになる。

DATA の中身は、relay からは 32 KiB ずつ送る。窓からは 64 KiB まで送ってよい。

## 接続の数

同時に開いておける接続は 256 本まで。超えた OPEN には CLOSE（`limit`）を返す。ブラウザが 1 つのホストに張る接続は数本で、いくつかのページを並べても足りる。上の流量の制御と合わせて、`kisui relay` のメモリを 64 MiB ほどに抑える。

## 中継ごと止める誤り

次の誤りは、続けると枠の切れ目や接続の取り違えが起きるので、接続ごとではなく `kisui relay` ごと止める（終了コード 1）。窓の誤りなので、起きないはず。

- 知らない種類の枠
- 中身が 65536 バイトを超える枠
- 枠の途中で標準入力が終わった
- 長さが 4 でない ACK
- 番号が増えていない OPEN

## 窓の側（#127）

窓の Rust の側（`app/src-tauri/src/relay.rs` と `open_url.rs`）の動き。

- **張る時機**：リモートのマシンの localhost 系の URL を初めて開くとき（`open_url_external`）。ssh の起こし方は `kisui attach` と同じ（`connection.rs` の `ssh_command`・askpass・キャッシュの kisui）で、`ssh -T <マシン> -- sh -c '… exec "$c" relay …'`。目印を待つのは 90 秒まで（ssh の質問に答える時間を含む）。目印が来なければ、ssh の標準エラー出力の最後か、kisui が入っていない（終了コード 97）ことを、URL を開けなかった理由として返す。
- **使い回し**：`kisui relay` はマシンごとに 1 本。手元の待ち受け（`127.0.0.1` の空きポート）は、マシンと URL のポートの組ごとに 1 つ。どちらも使い回す。URL の host（`localhost`・`127.0.0.1`・`[::1]`・`0.0.0.0`・`*.localhost`）は、どれも OPEN の host `localhost` にする（前の `ssh -L …:localhost:<ポート>` と同じ）。開く URL は `127.0.0.1:<手元のポート>` に書き換える。待ち受けを窓が自分で持つので、空きポートを調べてから ssh に渡すあいだに他に取られる心配が無い。
- **つながるかの確かめ**：URL を開く前に、そのポートへ OPEN を 1 つ送り、OPENED を待ってすぐ CLOSE する。CLOSE（`unreachable` など）が返ったら、ブラウザを開かずに「そのポートで誰も待っていない」を理由として返す（画面に出る）。`ssh -L` のときは、つなぎ先が断っても手元のポートは受けてしまい、分からなかった。
- **ブラウザの接続が失敗したとき**：開いたあと、ブラウザの接続の OPEN に CLOSE が返ったら（サーバーが止まった など）、ブラウザの接続をそのまま閉じる（ブラウザは「接続が切れた」「空の応答」を出す）。HTTP の 502 の頁を返すことはしない。https の URL では窓が TLS を話せず、http と https で見え方が変わるため。
- **ssh が切れたとき**：中継している接続は全部閉じる。待ち受けは残し、次にブラウザがつないだとき（頁の再読み込みなど）か、次に URL を開くときに張り直す。ブラウザの接続のために張り直して失敗したら、10 秒はブラウザの接続のためには張り直さない（開発サーバーの HMR のように頁がつなぎ直し続けると、そのたびに ssh を起こし、質問の窓を出してしまうため）。URL を開くときは、いつでも張り直す。
- **閉じる時機**：アプリの終了時。マシンとの接続（`kisui attach`）を切っても閉じない。開いた頁を見続けられるようにするため（前の `ssh -L` と同じ）。
- **流量の制御**：ブラウザから読んだ分は、ACK されていない分が 256 KiB を超えないように送る（超えるならブラウザを読むのを待つ）。relay から来た DATA は、ブラウザに書き終えてから ACK する。ブラウザへ書くのは接続ごとの糸で、遅いブラウザがほかの接続を止めない。
